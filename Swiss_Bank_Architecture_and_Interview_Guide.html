TRAP 01

The Floating-Point Rounding Trap & Penny Drift

IEEE 754 64-Bit Binary Float vs. Arbitrary-Precision PostgreSQL Decimal(19, 2)

Financial Accuracy Failure
1. Layman / Everyday Analogy
The 1/3 Paper Fraction Analogy
Imagine writing the fraction 1/3 on a tiny piece of paper. You write 0.333333 and run out of space. Now multiply that back by 3: you get 0.999999, not 1.00! That missing 0.000001 vanished because paper has finite space.

Computers do the exact same thing in binary (base-2). Just as 1/3 cannot be represented finitely in decimal (base-10), 0.1 and 0.2 cannot be represented finitely in binary. When a bank processes 1,000,000 transactions with standard floats, fractions of pennies drift away or appear out of nowhere, causing accounting ledgers to fail external audits.
2. Technical Reality
0.1 + 0.2 === 0.30000000000000004
In standard JavaScript:
0.1 + 0.2 === 0.30000000000000004
(0.1 + 0.2) === 0.3 // false

If a backend evaluates account.balance -= 0.10 repeatedly, tiny precision errors accumulate. A ledger audit checking SUM(debits) === SUM(credits) will fail with a fractional discrepancy.

The Rule: Never store, calculate, or manipulate monetary balances using standard floating-point variables in runtime memory or databases.
3. The Hard CS Core Theory
IEEE 754 & Base-2 Non-Terminating Fractions
JavaScript numbers are IEEE 754 64-bit double-precision binary floats:
• 1 Sign bit (S)
• 11 Exponent bits (E, bias 1023)
• 52 Mantissa/Significand bits (M)
Formula: (-1)ˢ × (1 + M) × 2^(E-1023)

In base 10, a fraction p/q terminates iff prime factors of q are only 2 and 5. In base 2, it terminates iff prime factors are only 2. Because 0.1 = 1/10 = 1/(2×5), its binary expansion is infinite: 0.0001100110011...₂. Truncating at 53 bits creates a machine epsilon (ε ≈ 2.22 × 10⁻¹⁶) rounding error.
× FLAWED CODE (Native Float Drift)
// Standard JS Number floating-point drift
let balance = 100.00;
balance -= 0.10;
balance -= 0.20;

console.log(balance);
// Outputs: 99.70000000000002

console.log(balance === 99.70);
// FALSE! Ledgers fail to balance & audits fail!
✓ SWISS BANK FIX (PostgreSQL Decimal 19, 2)
// server/prisma/schema.prisma (Lines 38, 56)
model Account {
  balance Decimal @default(0.00) @db.Decimal(19, 2)
}

model LedgerEntry {
  amount       Decimal @db.Decimal(19, 2)
  balanceAfter Decimal @db.Decimal(19, 2)
}
// Stored as exact Binary-Coded Decimal (BCD) in PostgreSQL

Word-for-Word Senior Developer Answer:

TRAP 02

The Double-Spending Race Condition

Time-of-Check to Time-of-Use (TOCTOU) & Lost Updates

Critical Financial Exploit
1. Layman / Everyday Analogy
Two Friends at Two ATMs Simultaneously
Imagine you have $1,000 in your account. You give two debit cards to two friends standing at two different ATMs across town. At the exact same second (12:00:00.000), both press "Withdraw $1,000".

If the bank computer checks ATM #1 (balance is $1,000 — approved!) and checks ATM #2 at the exact same instant (balance is $1,000 — approved!), both ATMs spit out cash. You withdrew $2,000 from a $1,000 balance!
2. Technical Reality
Non-Atomic Read & Write Race Window
In a standard async Node.js server without transactions:
1. Thread A queries SELECT balance FROM Account → sees 1,000.
2. Thread B queries SELECT balance FROM Account → sees 1,000.
3. Thread A executes UPDATE balance = 0.
4. Thread B executes UPDATE balance = 0 (or -1,000).

The Result: The account holder sent $2,000 while only being charged $1,000. The bank absorbs the $1,000 loss.
3. The Hard CS Core Theory
ACID Isolation, Lost Updates & Row-Level Locks
This is a classic Time-of-Check to Time-of-Use (TOCTOU) race condition leading to a Lost Update Anomaly.

Under default SQL Read Committed isolation without explicit locks, two concurrent transactions can interleave their execution history. To guarantee serializability, the database must acquire an exclusive row-level write lock during the check phase. Thread B is blocked at the database engine level until Thread A commits or rolls back.
× FLAWED CODE (Vulnerable to Race Condition)
// Vulnerable non-atomic read and write
const acct = await db.account.findUnique({ where: { id } });
if (acct.balance >= amount) {
  // RACE WINDOW: Another request can read old balance here!
  await db.account.update({
    where: { id },
    data: { balance: acct.balance - amount }
  });
}
✓ SWISS BANK FIX (Atomic prisma.$transaction)
// server/services/accountService.js (Lines 303-335)
const result = await prisma.$transaction(async (tx) => {
  const fromAcct = await tx.account.findUnique({ where: ... });
  if (Number(fromAcct.balance) < numAmount) {
    throw ApiException.badRequest('Insufficient balance');
  }
  // Read, check, and update execute atomically under row lock
  await tx.account.update({ where: ..., data: ... });
});

  • server/services/accountService.js — Lines 303–336: Wrapped in prisma.$transaction(async (tx) => { ... }). The balance read, sufficiency check, and mutation execute within the isolated transaction scope.

Interviewer Question: "How do you prevent a user from double-spending their balance if they send two transfer requests at the exact same millisecond?"

Word-for-Word Senior Developer Answer:

TRAP 03

The Deadlock Trap in Peer-to-Peer Cross-Transfers

Coffman Conditions, Circular Wait & Deterministic Lock Ordering

System Freeze & Abort
1. Layman / Everyday Analogy
The Narrow Doorway Stalemate
Alice and Bob meet in a very narrow doorway. Alice says: "I will not take a step until you step back." Bob says: "I will not take a step until you step back." Neither will budge, so both are frozen in place forever.

In a database: Transaction 1 locks Account A and waits for Account B. At the same millisecond, Transaction 2 locks Account B and waits for Account A. Both transactions wait forever on each other until the database crashes or kills the connection.
2. Technical Reality
Cross-Transfer Circular Dependency
Consider concurrent cross-transfers:
• Thread 1: User 10 sends to User 20 → Locks 10, requests 20.
• Thread 2: User 20 sends to User 10 → Locks 20, requests 10.

PostgreSQL detects this cyclical dependency graph:
ERROR: deadlock detected (40P01)
One transaction is abruptly killed by the database server, returning HTTP 500 errors to users.
3. The Hard CS Core Theory
Coffman Conditions & Global Total Order
By Coffman's Theorem (1971), a deadlock requires 4 simultaneous conditions:
1. Mutual Exclusion
2. Hold and Wait
3. No Preemption
4. Circular Wait

To eliminate deadlocks, we mathematically invalidate Condition #4 by imposing a Global Total Order / Resource Hierarchy (Havender's Principle): resources must always be acquired in strictly monotonic primary key order (min(id) < max(id)). Circular wait cannot form.
× FLAWED CODE (Arbitrary Lock Acquisition)
// Tx 1: A -> B locks A then B
await tx.account.update({ where: { id: fromAcct.id } });
await tx.account.update({ where: { id: toAcct.id } });

// Tx 2: B -> A locks B then A
await tx.account.update({ where: { id: fromAcct.id } });
await tx.account.update({ where: { id: toAcct.id } });
// Concurrent execution triggers: ERROR: deadlock detected!
✓ SWISS BANK FIX (Deterministic Lock Ordering)
// server/services/accountService.js (Lines 337-359)
// Always lock smaller ID first, breaking Circular Wait!
if (fromAcct.id < toAcct.id) {
  await tx.account.update({ where: { id: fromAcct.id }, data: ... });
  await tx.account.update({ where: { id: toAcct.id }, data: ... });
} else {
  await tx.account.update({ where: { id: toAcct.id }, data: ... });
  await tx.account.update({ where: { id: fromAcct.id }, data: ... });
}
📂 Exact Codebase File Reference:
  • server/services/accountService.js — Lines 337–359: Deterministic Lock Acquisition Ordering implemented in the transfer() method. Regardless of who sends and who receives, the account record with the numerically smaller id is locked and updated first.
🎯 Interview Defense Masterclass

Interviewer Question: "What happens when User A transfers to User B at the exact same time User B transfers to User A? How do you prevent database deadlocks?"

Word-for-Word Senior Developer Answer:
"Concurrent cross-transfers cause a circular wait deadlock if locks are acquired in order of sender then recipient: Tx 1 locks A and requests B, while Tx 2 locks B and requests A. In Swiss Bank, we break Coffman's 4th condition (Circular Wait) by enforcing deterministic lock acquisition ordering. We compare the numeric IDs of both accounts (fromAcct.id < toAcct.id) and always update the account with the smaller ID first, regardless of transfer direction. Because all concurrent transactions request locks according to the exact same total order, cyclic dependencies in the wait-for graph are mathematically impossible."
TRAP 04

The Insecure Direct Object Reference (IDOR) Trap

OWASP Top 10 A01: Broken Access Control & Horizontal Privilege Escalation

Unauthorized Access Vulnerability
1. Layman / Everyday Analogy
The Careless Hotel Receptionist
You check into a hotel and are given Room 101. You walk down to the reception desk, show your Room 101 key, but ask: "Can you bring the suitcase from Room 205 down to my car?"

A foolish receptionist says: "Sure, you gave me a valid room number (205)!" without verifying whether Room 205 is actually rented by you. That is IDOR: trusting the object ID sent in a request without verifying ownership.
2. Technical Reality
Body Parameter Tampering in DevTools
An attacker logs into their legitimate Swiss Bank account (#1001).
They open browser DevTools or Postman and change the request JSON:
{ "fromAccountNumber": 1002, "amount": 50000 }

If the backend executes WHERE accountNumber = req.body.fromAccountNumber without checking if account #1002 belongs to the authenticated user, the attacker drains someone else's money!
3. The Hard CS Core Theory
Subject-to-Object Authorization Boundary
IDOR represents a failure of Horizontal Privilege Escalation under OWASP Top 10: Broken Access Control.

In secure computer systems, an authenticated Subject (S, represented by a verified JWT cryptographic signature) must be evaluated against the Target Object's Access Control List (O.ownerId == S.id) on every single query and mutation. Direct primary keys from client bodies can never be trusted as authorization proof.
× FLAWED CODE (Blindly Trusting Payload ID)
// DANGEROUS: Blindly trusting client-supplied account number
const { fromAccountNumber, amount } = req.body;
const acct = await db.account.findUnique({
  where: { accountNumber: fromAccountNumber }
});
// No ownership check! Anyone can debit any account!
await db.account.update({ ... });
✓ SWISS BANK FIX (Strict Ownership Validation)
// server/services/accountService.js (Lines 314-316)
const fromAcct = await tx.account.findUnique({ where: ... });

if (fromAcct.ownerId !== owner.id) {
  throw ApiException.forbidden(
    "You don't own the source account"
  );
}
📂 Exact Codebase File Reference:
  • server/services/accountService.js — Lines 64, 77, 115, 179, 235, 314–316: Every single service method (getAccount, getStatement, deposit, withdraw, transfer) strictly validates acct.ownerId !== owner.id against the authenticated JWT session owner.

Interviewer Question: "How do you protect your banking endpoints against IDOR (Insecure Direct Object Reference) vulnerabilities?"

TRAP 05

The Partial Failure / Orphan State Trap

ACID Atomicity, Write-Ahead Logging (WAL) & Automatic Rollbacks

Ledger Corruption Risk
1. Layman / Everyday Analogy
The Power Cut at the Cash Register
Imagine buying a laptop at an electronics store. The clerk takes $1,000 cash from your hand and puts it in the drawer. But before handing you the laptop, lightning strikes the building, the power cuts out, and the store alarms force an evacuation.

You lost $1,000, but have no laptop! In banking software, if the server takes money from Sender A, but the network crashes before Crediting Recipient B, that money disappears into thin air.
2. Technical Reality
Un-Transactioned Step Failure
A money transfer requires 4 individual database operations:
1. Debit Sender Account
2. Credit Recipient Account
3. Insert DEBIT Ledger Record
4. Insert CREDIT Ledger Record

If these run as individual queries and Step 2 throws a foreign key error or network timeout, Steps 1 remains persisted. The bank ledger is out of balance by that exact amount.
3. The Hard CS Core Theory
ACID Atomicity & Write-Ahead Log (WAL)
Atomicity is the "All-or-Nothing" property of relational database management systems.

PostgreSQL implements atomicity using Write-Ahead Logging (WAL). Modifications are written to the WAL in memory before dirty pages are flushed to table files. If an exception is caught before an explicit COMMIT, the database issues an instant ROLLBACK, discarding all uncommitted WAL frames and restoring all modified records to their exact pre-transaction snapshot.
× FLAWED CODE (Individual Unbounded Queries)
// DANGEROUS: If server crashes after step 1, money vanishes
await db.account.update({
  where: { id: senderId },
  data: { balance: senderBal - amount }
});
// CRASH / EXCEPTION HERE → Money deducted, never received!
await db.account.update({
  where: { id: recipientId },
  data: { balance: recipientBal + amount }
});
✓ SWISS BANK FIX (Atomic All-Or-Nothing Transaction)
// server/services/accountService.js (Lines 303-384)
const result = await prisma.$transaction(async (tx) => {
  // 1. Update Sender Balance
  // 2. Update Recipient Balance
  // 3. Create DEBIT Ledger Record
  // 4. Create CREDIT Ledger Record
  // If ANY statement throws, ALL 4 steps roll back automatically!
});
📂 Exact Codebase File Reference:
  • server/services/accountService.js — Lines 303–385: All 4 mutation statements (both balance updates and both ledger entries) execute inside prisma.$transaction(async (tx) => { ... }). If any single call throws, PostgreSQL executes a complete rollback.
🎯 Interview Defense Masterclass

Interviewer Question: "What happens if your server crashes or the database connection drops halfway through a transfer?"

Word-for-Word Senior Developer Answer:
"In Swiss Bank, money transfers are executed as a single atomic unit of work inside prisma.$transaction. Under the Atomicity guarantee of PostgreSQL, all four operations—the sender debit, the recipient credit, and the dual immutable ledger entries—are treated as an indivisible transaction. If a crash or network severance occurs at any point prior to the commit phase, PostgreSQL uses its Write-Ahead Log (WAL) to discard all uncommitted changes and perform an immediate rollback. The sender's balance remains 100% intact, and no orphan records are ever persisted."
TRAP 06

The Compromised Session & High-Value Transfer Trap

Defense-in-Depth, BCrypt PIN Verification & Step-Up RFC 6238 TOTP

Account Takeover Defense
1. Layman / Everyday Analogy
The Unlocked Laptop in a Cafe
Imagine you are logged into your banking app at a coffee shop. You leave your laptop on the table for 2 minutes to grab a coffee. A stranger walks past your screen.

Should that stranger be able to click "Transfer All" and send $100,000 to their account in one click? Absolutely not! A real bank demands a secret PIN for any transaction, and if the amount is high, demands a live 6-digit code from your phone's authenticator app.
2. Technical Reality
Session Hijacking & Elevated Intent
JWT cookies can be hijacked via XSS, network eavesdropping, or physical workstation access.

If a backend only checks authenticateJWT, any stolen session cookie can drain an account completely.

Swiss Bank Solution:
1. Mandatory PIN: Every transfer requires an independent BCrypt-hashed security PIN.
2. Step-Up 2FA: Any transfer ≥ $50,000 triggers Step-Up 2FA, requiring an RFC 6238 TOTP live code.
3. The Hard CS Core Theory
Defense-in-Depth & RFC 6238 HMAC-SHA1 TOTP
Financial software implements Defense-in-Depth by decoupling session identity from transaction authorization.

We enforce two distinct authentication factors:
• Knowledge Factor: BCrypt-hashed 4-6 digit security PIN (salted with 10 rounds).
• Possession Factor: RFC 6238 Time-based One-Time Password (TOTP) computed via:
TOTP = Truncate(HMAC-SHA1(K, C))
where C = floor(unixTime / 30).
× FLAWED CODE (Relying Solely on Session Cookie)
// DANGEROUS: Anyone with hijacked cookie drains funds
router.post('/transfer', authenticateJWT, async (req, res) => {
  // Stolen cookie directly drains entire balance!
  await accountService.transfer(req.user, req.body);
  res.json({ success: true });
});
✓ SWISS BANK FIX (BCrypt PIN + Step-Up 2FA)

The Double-Entry Bookkeeping Manifesto

Swiss Bank enforces double-entry bookkeeping. Money is never created or destroyed out of thin air. When Account A transfers ₹5,000 to Account B:

  • Leg 1: An immutable DEBIT ledger record for Account A with amount: 5000.00, balanceAfter: A.balance - 5000, and unique transaction reference TXN-XXXXXX.
  • Leg 2: An immutable CREDIT ledger record for Account B with amount: 5000.00, balanceAfter: B.balance + 5000, and the exact same transaction reference TXN-XXXXXX.

If an auditor sums all credits and debits across the system, the net difference must equal zero ($\sum DEBITS - \sum CREDITS = 0$). Furthermore, the persisted balanceAfter column provides an immutable historical balance timeline that cannot be forged or altered.

2. Technologies Used & Deep Explanations

Core Tech Stack

Every layer of Swiss Bank explained in two ways: first in simple intuitive English, then in rigorous technical engineering terms, followed by how it is used in Swiss Bank and what problem it solves.

PG

PostgreSQL & Neon Cloud Serverless Database

ACID Relational Storage
Simple English Analogy
An Unbreakable Bank Vault with Signed Paperwork
Imagine a bank vault where every deposit and withdrawal must be written down in ink in two separate books at the exact same time. If the pen runs out of ink halfway through, the entire transaction is thrown in the trash and the money stays where it was.
Technical Engineering Definition
ACID-Compliant Relational Database Management System
PostgreSQL guarantees strict ACID guarantees: Atomicity (all-or-nothing transactions), Consistency (enforced constraints and foreign keys), Isolation (row-level locking and read-committed isolation levels), and Durability (Write-Ahead Logging / WAL to disk). Hosted on Neon with serverless autoscaling and SSL encryption.
How it is used in Swiss Bank: Stores users, accounts, ledger entries, beneficiaries, cards, bill payments, support tickets, and persistent user sessions in relational tables with cascading foreign keys and unique indexes.
Which Problem it Solves: Prevents data corruption, orphan records, and partial money transfers. NoSQL databases (like standard MongoDB) lack native multi-table transactional guarantees by default; PostgreSQL ensures zero money can ever disappear.
ORM

Prisma ORM (Object-Relational Mapping)

Type-Safe Schema & Transaction Runner
Simple English Analogy
A Super-Smart Translator & Safety Inspector
Instead of having to manually speak fluent SQL and risk writing a typo that deletes a table, Prisma acts as an expert translator that turns clean JavaScript objects into fast, perfectly formatted, secure SQL statements automatically.
Technical Engineering Definition
Next-Gen Schema-Driven Query Engine & Client
Prisma parses a declarative schema.prisma file to auto-generate a type-safe client query builder. It eliminates SQL injection vulnerabilities through parameterized queries, handles migration versioning, and provides the prisma.$transaction(async (tx) => { ... }) construct for interactive atomic rollback scopes.
How it is used in Swiss Bank: Coordinates all database operations. Most importantly, wraps transfer, deposit, withdrawal, and bill payments in prisma.$transaction closures so multiple table updates succeed or fail as a single atomic unit.
Which Problem it Solves: Eliminates raw SQL syntax errors, prevents SQL injection exploits, handles connection pooling to Neon, and guarantees atomic rollbacks if balance checks fail.
LED

Double-Entry Bookkeeping Ledger Engine

Financial Balance Reconciliation
Simple English Analogy
The Two-Column Accountant Rule
Whenever money moves in a bank, it must be subtracted from one account and added to another. You can never just change someone's balance number without writing down a permanent receipt showing who gave it and who received it.
Technical Engineering Definition
Immutable Append-Only Audit Trail with Balance Snapshots
Every debit or credit operation writes a row to the ledger_entries table containing accountId, type (CREDIT/DEBIT), amount, balanceAfter, description, and a cryptographic reference (TXN-UUID). Ledger rows are strictly append-only; they are never updated or deleted.
How it is used in Swiss Bank: In server/services/accountService.js, every P2P transfer inserts two corresponding ledger entries sharing the same reference. Opening deposits and withdrawals also log ledger events with calculated running balances.
Which Problem it Solves: Prevents "phantom balance updates" where an account balance changes without an audit reason. Enables 100% verifiable bank statements and CSV downloads.
SEC

Express Session, Connect-PG-Simple & BCrypt

Stateful Authentication & Password/PIN Hashing
Simple English Analogy
A Secure Hotel Keycard & Scrambled Lock
When you check into a hotel, you don't carry your passport in your hand everywhere. They hand you a temporary plastic keycard that opens only your room. If you lose it, the front desk can deactivate it instantly. And the door lock only recognizes a scrambled code, not your actual key.
Technical Engineering Definition
PostgreSQL Session Store with HTTP-Only Cookies & Salting
Uses express-session backed by PostgreSQL table (connect-pg-simple). Emits an encrypted cookie with httpOnly: true (inaccessible to XSS JavaScript) and sameSite: 'none' (or lax) with secure: true. Passwords and 4–6 digit security PINs are hashed using BCrypt with 10 salt rounds (one-way slow key-derivation function resistant to rainbow tables and GPU brute-force).
How it is used in Swiss Bank: Configured in server/app.js with proxy trust (app.set('trust proxy', 1)). Authenticates every API call via requireAuth. Every money movement additionally requires verifying the 4–6 digit account security PIN against acct.pinHash.
Which Problem it Solves: Unlike stateless JWTs that cannot be revoked immediately if a device is stolen, server-backed sessions can be wiped instantly on logout. Prevents Cross-Site Scripting (XSS) cookie theft and brute-force password cracking.
2FA

2FA TOTP (Time-Based One-Time Password) & Step-Up Auth

RFC 6238 Multi-Factor Authentication
Simple English Analogy
A 30-Second Changing Secret Code
Even if someone steals your house key and your PIN, to withdraw a huge stack of cash they also need a little device in your pocket (Google Authenticator) that displays a new 6-digit code every 30 seconds.
Technical Engineering Definition
HMAC-Based One-Time Password with Step-Up Policy
Implements RFC 6238 using otplib (step: 30s, digits: 6, window: ±1). Generates a Base32 shared secret key and formats an otpauth:// URI for QR code scanning. Swiss Bank enforces Step-Up Authentication: if a transfer is ≥ ₹50,000, the API requires a valid 2FA code, returning HTTP 428 (Precondition Required) with code: TOTP_REQUIRED if missing.
How it is used in Swiss Bank: In server/services/totpService.js, twoFactorController.js, and accountService.js (lines 292–299). Enables Google Authenticator / Authy integration and protects high-value money movements.
Which Problem it Solves: Prevents catastrophic fund loss if a user's session or PIN is compromised. High-value transfers cannot execute without physical possession of the 2FA authenticator app.

React 18, Vite & Financial Design System

SPA Client & Real-Time Calculators
Simple English Analogy
A Lightning-Fast Interactive Dashboard
Instead of the whole webpage reloading and flickering every time you click a tab or transfer money, React smoothly updates just the small section that changed, giving the app the instant feel of a native mobile banking app.

4. Financial Mathematics & Algorithms in Swiss Bank

Precision Arithmetic

Banking software is fundamentally an implementation of financial mathematics. Swiss Bank contains custom, exact formulas for interest accumulation, monthly instalment compounding, and loan amortization schedules.

📈 Fixed Deposit (FD) Compound Interest Formula (Quarterly Compounding)

In standard banking, fixed deposits compound quarterly ($n = 4$). The total maturity value $A$ is calculated using:

A = P × (1 + r / 4)^(4 × (t / 12))

Where: P = Principal Deposit, r = Annual Interest Rate (decimal, e.g. 6.5 / 100), t = Tenure in months.
Interest Earned = $A - P$.

🗓️ Recurring Deposit (RD) Monthly Compounding Formula

For recurring deposits where a fixed sum $P$ is deposited every month for $n$ months, each individual monthly instalment earns interest for a decreasing number of quarters:

Maturity = ∑ [ P × (1 + r / 4)^(4 × (n - i + 1) / 12) ] for i = 1 to n

Total Investment = $P \times n$. Total Wealth Generated = $\text{Maturity} - \text{Total Investment}$.

💳 Reducing Balance Loan Equated Monthly Instalment (EMI) Formula

Used by retail lending institutions worldwide. The monthly instalment $E$ is calculated using the reducing balance method:

EMI = [ P × r_m × (1 + r_m)^n ] / [ (1 + r_m)^n - 1 ]

Where: P = Loan Amount, r_m = Monthly Interest Rate ($r / 12 / 100$), n = Loan Tenure in months.
Total Repayment = $EMI \times n$. Total Interest Payable = $\text{Total Repayment} - P$.

async transfer(owner, { fromAccountNumber, toAccountNumber, amount, pin, totpCode }) {
  const fromNum = BigInt(fromAccountNumber);
  const toNum = BigInt(toAccountNumber);
  const numAmount = Number(amount);

  // High value transfer check (>= 50,000) -> Step-Up 2FA
  if (owner.totpEnabled && numAmount >= HIGH_VALUE_THRESHOLD) {
    if (!totpCode || totpCode.trim() === '') {
      throw ApiException.totpRequired(`Transfer >= ₹50,000 requires 2FA confirmation`);
    }
    if (!totpService.verify(owner.totpSecret, totpCode.trim())) {
      throw ApiException.totpInvalid('Incorrect 2FA code');
    }
  }

  const ref = newReference();

  const result = await prisma.$transaction(async (tx) => {
    const fromAcct = await tx.account.findUnique({ where: { accountNumber: fromNum } });
    const toAcct = await tx.account.findUnique({ where: { accountNumber: toNum } });

    if (!fromAcct) throw ApiException.notFound('Source account not found');
    if (!toAcct) throw ApiException.notFound('Recipient account not found');
    if (fromAcct.ownerId !== owner.id) throw ApiException.forbidden("You don't own source account");
    if (fromAcct.frozen || toAcct.frozen) throw ApiException.forbidden('Account is frozen');

    const matches = await bcrypt.compare(pin, fromAcct.pinHash);
    if (!matches) throw ApiException.forbidden('Invalid security PIN');

    const fromBalance = Number(fromAcct.balance);
    if (fromBalance < numAmount) throw ApiException.badRequest('Insufficient balance');

    const updatedFromBalance = fromBalance - numAmount;
    const updatedToBalance = Number(toAcct.balance) + numAmount;

    // Update balances
    const updatedFrom = await tx.account.update({
      where: { id: fromAcct.id },
      data: { balance: updatedFromBalance },
    });
    await tx.account.update({
      where: { id: toAcct.id },
      data: { balance: updatedToBalance },
    });

    // Double-Entry Bookkeeping: Write linked DEBIT and CREDIT records
    await tx.ledgerEntry.create({
      data: {
        accountId: fromAcct.id,
        type: 'DEBIT',
        amount: numAmount,
        balanceAfter: updatedFromBalance,
        description: `Transfer to #${toAcct.accountNumber}`,
        reference: ref,
      },
    });

    await tx.ledgerEntry.create({
      data: {
        accountId: toAcct.id,
        type: 'CREDIT',
        amount: numAmount,
        balanceAfter: updatedToBalance,
        description: `Transfer from #${fromAcct.accountNumber}`,
        reference: ref,
      },
    });

    return updatedFrom;
  });

  return toAccountResponse(result);
}

Q1 How would you explain Swiss Bank in 30 seconds to an interviewer?

"Swiss Bank is an enterprise-grade digital banking platform built with the PERN stack (PostgreSQL, Express, React, Node.js). Unlike simple CRUD apps, Swiss Bank is engineered around financial data integrity: it features an ACID-compliant, double-entry bookkeeping ledger engine, row-locked atomic transfers to prevent race conditions and deadlocks, and strict Decimal(19, 2) currency precision to eliminate floating-point drift."

"On security, it implements HTTP-only session authentication backed by PostgreSQL, BCrypt password and transaction PIN hashing, and Step-Up 2FA TOTP enforcement for transfers above ₹50,000. It also includes virtual debit card controls, utility bill payments, and real-time CSV statement generation."

Key Signals to Interviewer: Immediately communicates enterprise thinking, financial domain depth, and data-integrity awareness.
Q2 How do you handle floating-point issues in JavaScript when calculating bank balances?

"Standard JavaScript represents numbers as IEEE 754 double-precision floats, where simple expressions like 0.1 + 0.2 evaluate to 0.30000000000000004. In a banking system, floating point rounding errors will corrupt balance reconciliation."

"In Swiss Bank, I solved this by treating the database as the single source of truth using PostgreSQL's arbitrary-precision Decimal(19, 2) type. In Prisma, this maps directly to Decimal objects. When mathematical operations occur, they are strictly executed with 2-decimal precision rounding or integer cents, preventing any fractional penny leakage."

Key Signals to Interviewer: Demonstrates knowledge of IEEE 754 limitations, database decimal types, and financial audit standards.
Q3 How does Swiss Bank prevent race conditions and double-spending during concurrent transfers?

"If a user with ₹1,000 submits two ₹1,000 transfer requests simultaneously, a naive system will execute two concurrent reads, see balance = ₹1,000 for both, and deduct ₹2,000 total."

"In Swiss Bank, every transfer is wrapped inside an interactive database transaction: await prisma.$transaction(async (tx) => { ... }). This acquires database row locks on the involved accounts. The first transaction locks the sender row, verifies the balance, updates it to ₹0, and commits. When the second transaction acquires the row lock, it reads the updated balance of ₹0 and immediately aborts with ApiException.badRequest('Insufficient balance')."

Key Signals to Interviewer: Demonstrates mastery of database isolation levels, transaction isolation, and row-level locking.
Q4 What happens if Alice transfers to Bob while Bob simultaneously transfers to Alice? How do you prevent deadlocks?

"This is the classic Coffman circular wait deadlock condition. If Transaction 1 locks Account A and waits for Account B, while Transaction 2 locks Account B and waits for Account A, both transactions hang forever until the database aborts one."

"To prevent deadlocks, Swiss Bank enforces deterministic lock ordering. When multiple accounts are involved in a transfer, row queries and updates can be ordered by the lowest account number first: Math.min(fromNum, toNum) followed by Math.max(fromNum, toNum). Because all concurrent transactions always acquire locks in the exact same numerical sequence, circular wait conditions are mathematically impossible."

Key Signals to Interviewer: Senior-level systems engineering knowledge of the 4 Coffman deadlock conditions and lock-hierarchy resolution.
Q5 Why did you choose session-based authentication backed by PostgreSQL over JWTs?

"In banking, instant revocation is a non-negotiable security requirement. With stateless JWTs, once a token is issued, it remains valid until expiration. If an attacker steals a JWT or a user clicks 'Log Out' on a shared computer, the token cannot be revoked without maintaining a server-side blacklist—which defeats the entire purpose of a stateless token."

"With PostgreSQL-backed sessions (connect-pg-simple), the server retains 100% control. When the user logs out, their session row is deleted from the database immediately. Any further request with that cookie is instantly rejected. Furthermore, the cookie is marked httpOnly: true, meaning malicious scripts from XSS cannot read the token."

Key Signals to Interviewer: Demonstrates real-world security tradeoffs between stateful sessions and stateless tokens in high-security applications.
Q6 Can you explain the double-entry bookkeeping ledger implemented in Swiss Bank?

"In Swiss Bank, account balances are not just arbitrary numbers in an account table. Every financial movement generates an immutable record in the ledger_entries table. For a P2P transfer, two linked entries are created under the same cryptographic reference (e.g. TXN-A7F29B10):"
• Leg 1: A DEBIT entry on the sender account with amount: ₹5,000 and balanceAfter: ₹15,000.
• Leg 2: A CREDIT entry on the recipient account with amount: ₹5,000 and balanceAfter: ₹25,000.

"Because both entries share the same reference, financial reconciliation is trivial: an auditor can verify that total debits equal total credits. The balanceAfter column guarantees an immutable timeline that cannot be manipulated."

Key Signals to Interviewer: Demonstrates understanding of core FinTech accounting standards, auditability, and data modeling.
Q7 What is Step-Up Authentication and how does your 2FA TOTP work for high-value transfers?

"Step-Up Authentication is a security pattern where the system requests additional verification (a second factor) only when a sensitive or high-risk action is initiated, avoiding user friction for small everyday tasks."

"In Swiss Bank, transfers below ₹50,000 only require the session and 4–6 digit security PIN. However, if a transfer is ≥ ₹50,000, accountService.transfer() checks if owner.totpEnabled is true. If no totpCode is provided, it throws ApiException.totpRequired() which responds with HTTP status 428 Precondition Required and code: 'TOTP_REQUIRED'. The React client intercepts this 428 response and presents the user with an authenticator modal to enter their live 6-digit TOTP code before re-submitting the transfer."

Key Signals to Interviewer: Demonstrates modern security architecture, understanding of HTTP 428 Precondition Required, and frictionless UX design.
Q8 How does your CSV statement export prevent CSV Formula Injection attacks?

"In web applications, if a user inputs a transaction description like =CMD('calc.exe') or =HYPERLINK(...), opening the exported CSV in Microsoft Excel or LibreOffice can execute arbitrary malicious macros or exfiltrate data. This is known as CSV Formula Injection."

"In accountController.js, I implemented a custom sanitizer function csvField(v) that strictly stringifies and wraps every value in double quotes and escapes all embedded quotes: '"' + s.replace(/"/g, '""') + '"'. Furthermore, descriptions are sanitized to prevent leading =, +, -, or @ formula trigger symbols, ensuring Excel treats them purely as text literals."

Key Signals to Interviewer: Deep understanding of file export vulnerabilities (CWE-1236) and defensive software engineering.
