Chapter 1: The Zero-Knowledge Primer (Start Here!)

Ground-Up Definitions

If you have never built a full-stack app or feel confused by technical terms, this chapter explains every single concept in simple, everyday English. No prior knowledge required!

01

Client vs. Server vs. Database

Core Concept

Think of ordering food at a restaurant:

• The Client (Frontend / React): This is the customer sitting at the table looking at the menu. In software, this is your web browser (Chrome, Safari, Edge) running HTML, CSS, and React on your laptop or phone. It displays buttons, input boxes, and animations.

• The Server (Backend / Express & Node.js): This is the waiter and the kitchen staff. When you click a button in the browser, a message travels across the internet to the server. The server checks the rules (e.g., "Does this customer have enough money? Is their PIN correct?").

• The Database (PostgreSQL): This is the locked, fireproof ledger book in the manager's office. Even if the restaurant loses power or closes for the night, the ledger records who owns what and cannot be erased.

02

What is the "PERN" Stack?

Technology Suite

"PERN" is an acronym made of four tools that work together:

• P — PostgreSQL: The relational database that stores users, accounts, balances, and passbook entries in structured tables with strict rules.
• E — Express.js: The web framework that receives internet requests, directs traffic to the right function, and returns responses.
• R — React.js: The frontend library that renders the user interface on your screen dynamically without having to reload the webpage.
• N — Node.js: The runtime engine that lets computers run JavaScript code on the server (outside of a browser).

03

What is an HTTP Request & REST API?

Network Communication

Computers talk to each other by sending digital letters called HTTP Requests:

• GET: "Please read and send me information" (e.g. GET /api/accounts → sends your accounts list).
• POST: "Please create something new or execute an action" (e.g. POST /api/accounts/transfer with amount and PIN).
• HTTP Status Codes: The server's 3-digit reply code:
  • 200 OK: Success!
  • 201 Created: Successfully created a new account!
  • 400 Bad Request: You made a mistake (e.g. negative amount).
  • 401 Unauthorized: You are not logged in.
  • 403 Forbidden: You are logged in, but you don't own this account.
  • 404 Not Found: The account number does not exist.
  • 428 Precondition Required: Step-Up 2FA code is needed!
  • 500 Server Error: The server crashed unexpectedly.

04

What is JSON (JavaScript Object Notation)?

Data Format

When your browser sends data to the server, it writes it in a universal format called JSON. It looks like a simple list of labels and values:

{
  "toAccountNumber": 102938475612,
  "amount": 5000.00,
  "pin": "4321"
}
Every programming language in the world understands JSON, making it the universal language of the web.

05

Passwords, Hashing & Salts

Security Essentials

Rule #1 of Software: Never, ever store plain passwords in a database!

• Hashing (The Meat Grinder): You put fresh meat into a grinder and get sausage. But you can NEVER turn the sausage back into meat! That is a hash function (like BCrypt).
• Salt (The Secret Spice): What if two users both choose the password "secret"? If we ground them the same way, both would look identical. So we add random letters (a "Salt") to each password before grinding. Now, even identical passwords look completely different!

06

How Sessions & Cookies Work

Login Continuity

By default, the internet has total amnesia (it is "stateless"). When you click from page A to page B, the server forgets who you are!

• The Hotel Wristband Analogy: When you check into a waterpark hotel, the receptionist checks your passport once and snaps a waterproof plastic wristband on your arm.
• The Cookie: In web apps, the server sends a tiny piece of text called a Session Cookie (e.g. connect.sid). Your browser saves it. Every time you click a button or visit a page, your browser automatically flashes that wristband to the server so you stay logged in!

Chapter 2: High-Level System Design (HLD) & Request Flow

Architecture & Dataflow

High-Level Design (HLD) is the bird's-eye view of how all the servers, databases, and client devices communicate across the internet. Follow the exact step-by-step journey of a single money transfer.

The 4-Tier Architectural Hierarchy

Tier 1: Client Layer Browser UI

• React 18 & Vite: Single-page application.
• React Router v6: Handles page switching without reloading.
• AuthContext: Remembers logged-in user state in browser memory.

• Controllers: Extract HTTP body, query, and params.

Tier 4: Data Vault Database Engine

• Prisma ORM: Generates SQL queries with type safety.

• ACID Engine: Row-level locks, transactions, and Write-Ahead Logging (WAL).
• Decimal(19, 2): Arbitrary-precision monetary storage.

End-to-End Request Lifecycle: Sending ₹5,000 from Suraj to Bob

Let's trace what happens when customer Suraj logs in, opens the transfer modal, types Bob's account number, enters ₹5,000, types his 4-digit PIN, and clicks "Send Money":

Step 1: The Browser React Action

The React component (DashboardPage.jsx) collects form inputs: toAccountNumber, amount = 5000, pin = '4321'. It calls api('/api/accounts/transfer', { method: 'POST', body: JSON.stringify(payload) }).

Step 2: Traveling Across the Internet

The browser bundles an HTTP POST request packet. Crucially, because credentials: 'include' was configured, the browser automatically attaches the encrypted cookie header: Cookie: connect.sid=s%3A7a8f9b....

Step 3: Server Entry & Port 8080 (server.js)

The packet arrives at the Node.js TCP socket on port 8080 and is handed to the Express application sitting in app.js.

Step 4: The Middleware Gauntlet (app.js)

1. Helmet: Approves HTTP headers.
2. CORS: Checks origin domain against whitelist.
3. express.json(): Parses raw JSON text into JavaScript object (req.body).
4. Session Middleware: Reads connect.sid, queries PostgreSQL session table, finds Suraj's session, and sets req.session.userId = 1.

Step 5: Router & Route Guard (accountRoutes.js)

accountRoutes.js runs requireAuth. It verifies req.session.userId, loads Suraj's full user object from PostgreSQL, attaches it to req.user, and calls accountController.transfer.

Step 6: The Controller Handoff (accountController.js)

accountController.transfer(req, res, next) delegates the task to the core business engine: await accountService.transfer(req.user, req.body).

Step 7: The Money Movement Vault (accountService.js)

The service opens an atomic transaction: await prisma.$transaction(async (tx) => { ... }):
• Verifies Suraj owns source account (IDOR check).
• Compares PIN against pinHash with bcrypt.compare.
• Verifies Suraj's balance ≥ ₹5,000.
• Deadlock prevention: Updates the lower account ID first.
• Writes matched DEBIT and CREDIT ledger entries under transaction reference TXN-XXXXXX.

Step 8: PostgreSQL Commits to Disk

PostgreSQL writes the changes to its Write-Ahead Log (WAL), locks release, and the transaction commits permanently.

Step 9: Returning to the User

The controller sends HTTP 200 with the updated account balance in JSON. The React frontend intercepts the response, triggers a green success toast ("Transfer completed!"), and refreshes the balance counter on screen without reloading the page!

6 Software Design Patterns Used in Swiss Bank

1. Layered Architecture (Separation of Concerns):

Routes only receive requests; Controllers only unpack data; Services only execute business logic; Prisma only talks to SQL. No layer does another layer's job!

2. Singleton Pattern (prisma.js):

Instead of creating 100 new database connections, config/prisma.js creates a single PrismaClient instance shared by the entire server.

3. Factory Pattern (ApiException.js):

Instead of writing new ApiException(400, 'msg') everywhere, static factory methods like ApiException.badRequest('msg') build errors cleanly.

4. DTO Pattern (Data Transfer Objects):

Functions like toUserResponse() strip out sensitive fields (like passwordHash) before sending JSON back to the browser.

5. Lazy Provisioning (cardService.js):

Virtual cards are generated only when a user requests their card for the first time via getOrCreate(), saving database storage.

6. Unit of Work / Transaction Pattern:

prisma.$transaction(async (tx) => { ... }) treats multiple database updates as an indivisible atomic unit that succeeds or fails together.

Chapter 4: The 6 Mission-Critical Financial Traps

Senior Engineering Deep Dives

Why can't you build a bank like a standard blog or shopping cart? In banking, a single unhandled race condition or rounding glitch causes real financial theft, regulatory fines, and legal liability. Here is how Swiss Bank defends against all 6 traps.

01

Trap 1: The Floating-Point Rounding Trap & Penny Drift

IEEE 754 Binary Floating-Point vs Arbitrary-Precision Decimal Storage

Penny Leakage
🐣 Layman Language
The 1/3 Paper Analogy
Try writing 1/3 on a small note. You write 0.333333 and run out of space. Multiply it back by 3: you get 0.999999, not 1.00! That 0.000001 was lost because paper is finite.

In computers, numbers are stored in base-2 (binary). Just as 1/3 cannot be written finitely in decimal, 0.1 and 0.2 cannot be written finitely in binary. In JavaScript, 0.1 + 0.2 === 0.30000000000000004. Over millions of transactions, tiny fractions of pennies leak out or appear out of nowhere, breaking accounting audits.
👔 Technical Interview Language
IEEE 754 64-Bit Float vs Decimal(19, 2)
Standard JavaScript uses 64-bit binary floating-point numbers. In base 2, fractions only terminate if the denominator is a power of 2 ($2^k$). Because $0.1 = 1/10 = 1/(2 imes 5)$, its binary representation is an infinite repeating fraction ($0.000110011..._2$). Truncating at 53 bits introduces machine epsilon ($epsilon approx 2.22 imes 10^{-16}$) error.

Swiss Bank Fix: In schema.prisma (lines 38, 56), balances and ledger amounts are configured as @db.Decimal(19, 2). PostgreSQL stores these as exact Binary Coded Decimals without binary floating-point approximation.
02

Trap 2: The Double-Spending Race Condition

Time-of-Check to Time-of-Use (TOCTOU) & Lost Updates

Double Withdrawal
🐣 Layman Language
Two Friends at Two ATMs Simultaneously
You have ₹1,000 in your account. You give two debit cards to two friends at two separate ATMs. At the exact same second (12:00:00.000), both press "Withdraw ₹1,000".

If the bank software checks ATM #1 (balance ₹1,000 — approved!) and ATM #2 (balance ₹1,000 — approved!), both ATMs spit out cash. You withdrew ₹2,000 from a ₹1,000 balance!
👔 Technical Interview Language
Atomic Transactions & Row-Level Write Locks
This is a classic Time-of-Check to Time-of-Use (TOCTOU) race condition.

Swiss Bank Fix: In accountService.js (lines 303–384), all balance checking, deduction, and ledger creation are executed inside an atomic prisma.$transaction(async (tx) => { ... }). PostgreSQL acquires an exclusive row write lock on the sender's account. Any concurrent transaction is forced to wait until the first commits, at which point it reads the depleted balance and fails the sufficiency check (fromBalance < numAmount).
03

Trap 3: The Deadlock Trap in Peer-to-Peer Cross-Transfers

Coffman Conditions, Circular Wait & Deterministic Lock Ordering

System Freezing
🐣 Layman Language
The Narrow Doorway Stalemate
Alice and Bob meet in a narrow doorway. Alice says: "I will not step back until you step forward." Bob says: "I will not step back until you step forward." Both stand there frozen forever.

In a bank: Alice sends to Bob (locks Alice, waits for Bob). At the same millisecond, Bob sends to Alice (locks Bob, waits for Alice). Both wait on each other until the database crashes!
👔 Technical Interview Language
Deterministic Global Total Order (Havender's Principle)
By Coffman's Theorem (1971), deadlocks require Circular Wait ($T_1 o R_2 o T_2 o R_1$).

Swiss Bank Fix: In accountService.js (lines 337–360), we enforce deterministic lock acquisition ordering by comparing account primary keys:
if (fromAcct.id < toAcct.id) { update(fromAcct); update(toAcct); } else { update(toAcct); update(fromAcct); }.
Because every transaction in the system acquires locks in the exact same numerical order, wait-for cycles are mathematically impossible!
04

Trap 4: Insecure Direct Object Reference (IDOR)

OWASP Top 10 A01: Broken Access Control & Parameter Tampering

Theft by DevTools
🐣 Layman Language
The Careless Hotel Receptionist
You show your key for Room 101, but ask: "Can you bring down the suitcase inside Room 205?" A bad receptionist hands you Room 205's suitcase without checking if you actually rented Room 205.

In banking: A user opens browser DevTools or Postman and changes fromAccountNumber: 1002 (someone else's account number) to drain someone else's money!
👔 Technical Interview Language
Horizontal Privilege Escalation Prevention
Direct object IDs sent in HTTP request payloads must never be trusted for authorization.

Swiss Bank Fix: In accountService.js (lines 64, 77, 115, 314–316), the service layer extracts the authenticated user ID strictly from the verified session (req.user.id). Before any query or debit, it verifies:
if (fromAcct.ownerId !== owner.id) throw ApiException.forbidden("You don't own the source account");.
05

Trap 5: Partial Failure / Orphan State Trap

ACID Atomicity & Write-Ahead Logging (WAL) Rollbacks

Money Vanishing
🐣 Layman Language
The Power Cut at Checkout
You hand ₹50,000 cash to a store clerk. The clerk takes the money. But before handing you the television, lightning strikes, the power cuts out, and store alarms force everyone outside. You lost ₹50,000 and have no television!

In software: If ₹5,000 is debited from Sender A, but the network drops before Crediting Recipient B, that ₹5,000 vanishes into thin air.
👔 Technical Interview Language
All-or-Nothing ACID Atomicity
A transfer requires 4 operations: Debit Sender, Credit Recipient, Insert DEBIT ledger entry, Insert CREDIT ledger entry.

Swiss Bank Fix: All 4 operations reside in a single prisma.$transaction(async (tx) => { ... }). If an unhandled exception, network severed connection, or server restart occurs before the final line, PostgreSQL uses its Write-Ahead Log (WAL) to discard all changes. The sender's balance remains 100% untouched.
06

Trap 6: Compromised Session & High-Value Transfers

Defense-in-Depth, BCrypt PIN & Step-Up RFC 6238 TOTP

Account Takeover
🐣 Layman Language
The Unlocked Laptop in a Cafe
You leave your laptop on a coffee shop table for 2 minutes to grab a coffee. A stranger walks past your open screen. Should they be able to click "Transfer All" and drain ₹5,00,000 with one click?

NO! A bank demands your Secret 4-Digit PIN for every transfer, and if the amount is high, demands a live 6-digit code from your phone's Google Authenticator app.
👔 Technical Interview Language
Step-Up Multi-Factor Re-Authentication of Intent
A session cookie proves who is logged in, but not intent for dangerous operations.

Swiss Bank Fix:
1. Knowledge Factor: Every money movement mandates a 4-digit PIN verified via bcrypt.compare(pin, fromAcct.pinHash).
2. Possession Factor: Any transfer ≥ ₹50,000 triggers Step-Up 2FA (ApiException.totpRequired() responding with HTTP 428), requiring an RFC 6238 TOTP live code from Google Authenticator.

Chapter 7: The Master 30-Question Interview Defense

Verbatim Senior Scripts

Click on any card to reveal the exact, verbatim senior developer response you can memorize and speak out loud in your technical interviews.

Q01 Can you explain the high-level architecture of Swiss Bank?

"Swiss Bank is an enterprise-grade full-stack banking platform built on the PERN stack: PostgreSQL, Express, React, and Node.js. The architecture is strictly decoupled into a client Single Page Application built with React and Vite, communicating via a RESTful JSON API with an Express backend."

"At the data layer, we use PostgreSQL hosted on Neon, managed through Prisma ORM. Crucially, all financial mutations enforce ACID transactional boundaries, double-entry bookkeeping with immutable ledger entries, and deterministic lock ordering to guarantee zero deadlocks and zero balance drift."

Q02 Why did you choose PostgreSQL over MongoDB for a banking system?

"Banking software demands strict ACID guarantees (Atomicity, Consistency, Isolation, and Durability). Financial systems cannot tolerate eventual consistency or lost updates."

"PostgreSQL provides mature relational constraints, foreign keys with cascading rules, write-ahead logging (WAL), row-level write locks, and arbitrary-precision decimal support (Decimal(19, 2)). A document store like MongoDB lacks native multi-table schema constraints and is vulnerable to schema drift during high-concurrency ledger operations."

Q03 Why can't you use standard JavaScript numbers to store and calculate currency?

"JavaScript numbers are 64-bit IEEE 754 binary floating-point numbers. In binary (base-2), base-10 fractions like 0.1 and 0.2 cannot be represented as finite terminating decimals, resulting in infinite repeating binary fractions. Consequently, 0.1 + 0.2 evaluates to 0.30000000000000004."

"In banking, accumulating floating-point drift across millions of transactions breaks double-entry reconciliation (∑ Debits ≠ ∑ Credits). In Swiss Bank, we eliminate this vulnerability by defining all balance and transaction fields in PostgreSQL as Decimal(19, 2) via Prisma, ensuring exact binary-coded decimal precision down to the exact cent."

Q04 How do you prevent double-spending when a user clicks 'Transfer' twice simultaneously?

"We prevent double-spending by encapsulating balance validation, deduction, and ledger insertion within an atomic prisma.$transaction block. Under PostgreSQL's transactional engine, the first transaction acquires an exclusive row-level write lock on the sender's account record."

"The second concurrent transaction is blocked at the database level until the first commits. When the second transaction unblocks and reads the balance, it observes the already-debited funds, fails the balance check (fromBalance < numAmount), and throws an ApiException.badRequest('Insufficient balance')."

Q05 How do you prevent database deadlocks in concurrent peer-to-peer transfers?

"Cross-transfers (User A transfers to User B while User B transfers to User A) can trigger a deadlock under the Coffman Circular Wait condition if locks are acquired arbitrarily based on sender then receiver."

"In Swiss Bank, we break Coffman's 4th condition (Circular Wait) by implementing deterministic lock acquisition ordering. In accountService.transfer(), we compare the primary keys (fromAcct.id < toAcct.id) and always update the account with the smaller ID first, regardless of transfer direction. Because all concurrent transactions acquire locks according to the exact same total order, wait-for cycles are mathematically impossible."

Q06 What is IDOR and how does Swiss Bank protect against it?

"Insecure Direct Object Reference (IDOR) is an access control vulnerability where an application uses client-supplied input to access database objects directly without verifying ownership. For example, an attacker alters fromAccountNumber in DevTools to debit someone else's account."

"In Swiss Bank, client payloads are never trusted for authorization. Our service layer extracts the authenticated user ID strictly from the verified session (req.user.id). Prior to any balance check or mutation, our service asserts: if (fromAcct.ownerId !== owner.id) throw ApiException.forbidden(). Any parameter tampering is immediately rejected with HTTP 403 Forbidden."

Q07 What is Step-Up Authentication and how is it implemented?

"Step-Up Authentication is a defense-in-depth pattern where a second factor is requested only when a high-risk action is performed, reducing user friction for low-risk actions."

"In Swiss Bank, transfers below ₹50,000 only require the session and 4-digit PIN. However, if a transfer is ≥ ₹50,000, accountService.transfer() checks if owner.totpEnabled is active. If no totpCode is provided, it throws an ApiException.totpRequired() responding with HTTP 428 Precondition Required. The React client catches this and displays the 2FA modal asking for their Google Authenticator code."

Q08 Why do you use express-session with connect-pg-simple instead of in-memory sessions?

"Default in-memory session storage (MemoryStore) causes severe production issues: it leaks memory, cannot scale across multiple horizontal server instances, and loses all active user sessions whenever the Node.js process restarts or deploys."

"By using connect-pg-simple, all session state is persisted inside the PostgreSQL session table. Multiple server instances can share session state, server restarts never disconnect users, and expired sessions are automatically pruned using database timestamps."

Q09 What is Double-Entry Bookkeeping and how is it enforced?

"Double-entry bookkeeping is the fundamental accounting principle that money is never created or destroyed out of nothing. Every transaction must consist of at least two equal and opposite entries: a Debit and a Credit."

"In Swiss Bank, when Account A sends ₹5,000 to Account B, our transaction creates two paired immutable records in LedgerEntry sharing the exact same reference code (ref): one DEBIT record for Account A and one CREDIT record for Account B. The net sum across the entire ledger is always zero (∑ Debits = ∑ Credits)."

Q10 Why do you store account numbers as BigInt instead of standard JavaScript Number?

"In JavaScript, standard numbers are 64-bit floats. The maximum integer that can be safely represented without losing precision is Number.MAX_SAFE_INTEGER ($2^{53} - 1 = 9,007,199,254,740,991$)."

"Standard banking account numbers are 12 to 16 digits long. If an account number exceeds 53 bits, standard JavaScript silently truncates or rounds the lowest digits, causing money to be credited to the wrong customer! We use JavaScript's native BigInt and PostgreSQL's BigInt to support arbitrarily large numbers safely."

Q11 How does offline Google Authenticator generate 2FA codes without internet?

"It uses the RFC 6238 Time-based One-Time Password (TOTP) algorithm. During setup, the server and phone share a Base32 secret key via QR code. Both the phone and server divide the current Unix epoch time by 30 seconds to produce a counter $C$. Both compute $ ext{HMAC-SHA1}( ext{Secret}, C)$ and dynamically truncate it to a 6-digit number. Because both look at the same world clock and share the secret, both generate the exact same code without needing internet."

Q12 What does 'BigInt.prototype.toJSON' do in your Prisma config?

"In ECMAScript standards, JSON.stringify() throws a TypeError: Do not know how to serialize a BigInt because BigInt could lose precision when parsed by other JSON parsers. In server/config/prisma.js, monkey-patching BigInt.prototype.toJSON = function() { return Number(this); } instructs Express to serialize BigInts as numbers, preventing 500 crashes across all account API endpoints."

Q13 How does your CSV statement export prevent CSV Formula Injection attacks?

"In accountController.js, the csvField(v) sanitizer ensures every field is strictly stringified and wrapped in double quotes with internal double quotes escaped ('"' + s.replace(/"/g, '""') + '"'). Furthermore, formula trigger characters (=, +, -, @) are sanitized so Excel treats them strictly as text literals, mitigating CWE-1236 Formula Injection."

Q14 What does 'app.set("trust proxy", 1)' do in app.js?

"When deployed on cloud platforms like Render or Vercel, the Node.js application sits behind a reverse proxy (like Nginx or Cloudflare) that terminates SSL/TLS. Without app.set('trust proxy', 1), Express considers incoming connections to be insecure HTTP, refusing to send cookies marked with secure: true. Trust proxy enables Express to inspect the X-Forwarded-Proto: https header and correctly deliver secure cookies."

Q15 How would you scale Swiss Bank to handle 10,000 transfers per second?

"1. Database Connection Pooling: Introduce PgBouncer in front of PostgreSQL to handle thousands of concurrent client connections without connection overhead."

"2. Horizontal Read Scaling: Add PostgreSQL read-replicas for balance checks, user lookups, and statement queries, reserving the primary instance exclusively for write transactions."

"3. Distributed Caching & Queuing: Introduce Redis for session storage and rate limiting, and an event-driven queue (Kafka or RabbitMQ) for asynchronous non-blocking operations like notification dispatch, statement PDF generation, and fraud telemetry."
