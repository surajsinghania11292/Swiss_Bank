Table: User (model User)

Stores customer profiles and credentials

🐣 Layman Language
This is the bank customer's official file. It holds their name, email, phone number, PAN card number, and address.

Identity & Multi-Factor Entity
The User table represents the authenticated principal. Features:

• passwordHash computed via BCrypt with 10 salt rounds.
• role enum ('USER' vs 'ADMIN') enabling Role-Based Access Control (RBAC).
• totpSecret and totpEnabled storing RFC 6238 Base32 secrets for Step-Up 2FA.

02

Table: Account (model Account)

Holds account balances and transaction safety rules

server/prisma/schema.prisma (Lines 32-47)
🐣 Layman Language
A single user can have bank accounts. This table stores:
• accountNumber (BigInt): Why BigInt? Normal numbers stop working after 9,007,199,254,740,991. A 12-digit account number needs BigInt so the computer never confuses digits!
• balance (Decimal 19, 2): Why not Float? Float loses fractions of pennies! Decimal stores exact digits down to 2 decimal places.
• pinHash: The 4-digit ATM/Transfer PIN, encrypted with BCrypt.
• frozen: A true/false switch. If the police or bank manager suspects fraud, they freeze the account and no money can leave.
👔 Technical Interview Language
Financial Ledger Account Record
The Account table represents the mutable monetary balance container.
• balance Decimal @db.Decimal(19, 2): Stored in PostgreSQL as arbitrary-precision BCD, eliminating IEEE 754 float drift.
• accountNumber BigInt @unique: Prevents 64-bit integer truncation above JavaScript's Number.MAX_SAFE_INTEGER ($2^{53}-1$).
• version Int @default(1): Prepared for Optimistic Concurrency Control (OCC).
• onDelete: Cascade: Foreign key relation linked to User.id.
03

Table: LedgerEntry (model LedgerEntry)

The immutable double-entry passbook

server/prisma/schema.prisma (Lines 51-64)
🐣 Layman Language
Think of a physical bank passbook printed in ink.

Whenever you deposit, withdraw, or transfer money, a new row is stamped here. It records the date, whether money entered (CREDIT) or left (DEBIT), how much money moved, and what your exact balance became right after (balanceAfter).

Golden Rule: Rows in this table are NEVER edited and NEVER deleted. Even if an error happens, the bank writes a new correction row rather than erasing history!
👔 Technical Interview Language
Immutable Double-Entry Ledger Store
The LedgerEntry table fulfills statutory auditing requirements:
• type: Discriminator enum (DEBIT vs CREDIT).
• reference: Unique UUID / transaction code (e.g. TXN-179482...) linking paired transfer legs together.
• balanceAfter: Point-in-time balance snapshot creating an append-only audit trail.
• @@index([accountId]) & @@index([reference]): B-tree indexes guaranteeing $O(log N)$ historical statement queries.

4. Security & Authentication: How Login Works

authController.js & auth.js

How do we verify who the user is without ever risking their password or session?

🐣 Layman Language
How Password Salting & BCrypt Work
If User A and User B both choose the password "password123", should they look the same in the database?

NO! If they looked the same, a hacker who cracks one password gets both.

Instead, BCrypt adds a Salt (a random string of letters, like adding a pinch of salt to food). Even with the exact same password, User A becomes $2b$10$abc123xyz... and User B becomes $2b$10$999qqq777.... Hackers cannot use precomputed tables (Rainbow Tables) to crack them!
👔 Technical Interview Language
Cryptographic Password Hashing & Session Guard
Swiss Bank employs BCrypt with an adaptive work factor of 10 rounds:
• Incorporates a unique, cryptographically random 128-bit salt per user.
• Computationally expensive key-derivation function designed to resist FPGA and GPU brute-force attacks.
• Session tokens are stored in an HttpOnly cookie, shielding them from Cross-Site Scripting (XSS) token theft.
• requireAuth middleware retrieves the session ID, queries PostgreSQL, and binds the hydrated user entity to req.user.
server/middlewares/auth.js — Protected Route Middleware
// How we protect banking endpoints from unauthorized visitors
export async function requireAuth(req, res, next) {
  // 1. Check if the user has a valid active session
  if (!req.session || !req.session.userId) {
    return next(ApiException.unauthorized('Not authenticated'));
  }

  // 2. Fetch user from PostgreSQL
  const user = await prisma.user.findUnique({
    where: { id: req.session.userId },
  });

  // 3. If user was deleted or session is expired, kick them out
  if (!user) {
    req.session.destroy(() => {});
    return next(ApiException.unauthorized('Not authenticated'));
  }

  // 4. Attach verified user to request so next functions know who is calling
  req.user = user;
  next();
}

5. The 2FA Engine: How Offline Authenticator Works

totpService.js & RFC 6238

How does Google Authenticator know the exact same 6-digit code as your backend server even when your phone has NO internet and is on Airplane Mode?

🐣 Layman Language
The Shared Secret & World Clock Magic
When you scan the QR code during 2FA setup, Swiss Bank gives your phone a secret password (e.g. JBSWY3DPEHPK3PXP). Both your phone and the server now know this secret password.

Now, both your phone and the server look at the world clock. Every 30 seconds, both run a mathematical puzzle on that secret password and the current 30-second block of time.

Because the secret password is the same, and the time is the same, both sides arrive at the exact same 6-digit number! No internet connection needed on the phone!
👔 Technical Interview Language
RFC 6238 Time-Based One-Time Password (TOTP)
Swiss Bank utilizes the otplib implementation of RFC 6238:
• Time Step ($X$): 30 seconds.
• Counter ($C$): $C = lfloor T / X floor$, where $T$ is the current Unix epoch timestamp.
• Hash Algorithm: HMAC-SHA1 computed over shared secret key $K$ and Counter $C$:
$$ ext{HMAC} = ext{HMAC-SHA-1}(K, C)$$
• Dynamic Truncation extracts a 4-byte dynamic binary code, modulo $10^6$, yielding a 6-digit integer.
• Window Tolerance: $pm 1$ step (90 seconds total) compensating for client clock drift.

6. The Money Engine: Transfers & The 6 Critical Traps

accountService.js Walkthrough

The core of Swiss Bank is server/services/accountService.js. Here is how peer-to-peer transfers work and how all 6 classic financial software bugs are solved.

server/services/accountService.js — The transfer() Method Step-by-Step
async transfer(owner, { fromAccountNumber, toAccountNumber, amount, pin, totpCode }) {
  // STEP 1: Sanitize Inputs and Convert to Safe Numbers
  const fromNum = BigInt(fromAccountNumber);
  const toNum = BigInt(toAccountNumber);
  const numAmount = Number(amount);

  if (fromNum === toNum) throw ApiException.badRequest('Cannot transfer to the same account');
  if (!numAmount || numAmount <= 0) throw ApiException.badRequest('Transfer amount must be positive');

  // STEP 2: Step-Up 2FA Check for High-Value (>= ₹50,000)
  if (owner.totpEnabled && numAmount >= HIGH_VALUE_THRESHOLD) {
    if (!totpCode || totpCode.trim() === '') {
      throw ApiException.totpRequired('Transfer ≥ ₹50,000 — enter 2FA code to confirm');
    }
    if (!totpService.verify(owner.totpSecret, totpCode.trim())) {
      throw ApiException.totpInvalid('Incorrect 2FA code');
    }
  }

  const ref = newReference(); // Generate unique TXN-XXXXXX code

  // STEP 3: Enter the Atomic Database Vault (prisma.$transaction)
  const result = await prisma.$transaction(async (tx) => {
    const fromAcct = await tx.account.findUnique({ where: { accountNumber: fromNum } });
    const toAcct = await tx.account.findUnique({ where: { accountNumber: toNum } });

    if (!fromAcct) throw ApiException.notFound('Source account not found');
    if (!toAcct) throw ApiException.notFound('Recipient account not found');

    // STEP 4: Prevent IDOR (Check if user owns source account)
    if (fromAcct.ownerId !== owner.id) {
      throw ApiException.forbidden("You don't own the source account");
    }
    if (fromAcct.frozen || toAcct.frozen) {
      throw ApiException.forbidden('Account is frozen — contact support');
    }

    // STEP 5: Verify Secret 4-Digit Security PIN
    const matches = await bcrypt.compare(pin, fromAcct.pinHash);
    if (!matches) throw ApiException.forbidden('Invalid security PIN');

    // STEP 6: Check Balance Sufficiency
    const fromBalance = Number(fromAcct.balance);
    if (fromBalance < numAmount) throw ApiException.badRequest('Insufficient balance');

    const updatedFromBalance = fromBalance - numAmount;
    const updatedToBalance = Number(toAcct.balance) + numAmount;

    // STEP 7: Prevent Deadlocks — Deterministic Lock Ordering (min ID first)
    let updatedFrom;
    if (fromAcct.id < toAcct.id) {
      updatedFrom = await tx.account.update({ where: { id: fromAcct.id }, data: { balance: updatedFromBalance } });
      await tx.account.update({ where: { id: toAcct.id }, data: { balance: updatedToBalance } });
    } else {
      await tx.account.update({ where: { id: toAcct.id }, data: { balance: updatedToBalance } });
      updatedFrom = await tx.account.update({ where: { id: fromAcct.id }, data: { balance: updatedFromBalance } });
    }

    // STEP 8: Create Paired Double-Entry Immutable Ledger Records
    await tx.ledgerEntry.create({
      data: { accountId: fromAcct.id, type: 'DEBIT', amount: numAmount, balanceAfter: updatedFromBalance, reference: ref, description: 'Transfer to #' + toAcct.accountNumber }
    });
    await tx.ledgerEntry.create({
      data: { accountId: toAcct.id, type: 'CREDIT', amount: numAmount, balanceAfter: updatedToBalance, reference: ref, description: 'Transfer from #' + fromAcct.accountNumber }
    });

    return updatedFrom;
  });
  return result;
}

Quick Summary: The 6 Traps & How Swiss Bank Solves Them

1. Floating-Point Drift:

0.1 + 0.2 === 0.30000000000000004. Solved by PostgreSQL Decimal(19, 2) storing exact digits.

2. Double-Spending Race:

Two simultaneous clicks withdraw ₹2,000 from ₹1,000. Solved by prisma.$transaction with row-level locks.

3. Deadlock Trap:

A sends to B while B sends to A; both freeze forever. Solved by ordering locks: lower id is always updated first!

4. IDOR Privilege Escalation:

Attacker changes account number in Postman. Solved by validating fromAcct.ownerId !== req.user.id on every call.

5. Partial Failure / Orphan State:

Server crashes after taking sender's money. Solved by ACID Atomicity: all 4 steps succeed together or roll back 100%.

6. Compromised Session Trap:

Stolen cookie tries to empty account. Solved by mandatory BCrypt PIN on all transfers + Step-Up 2FA for amounts ≥ ₹50,000.

Q01 Can you explain the high-level architecture of your Swiss Bank project?

"Swiss Bank is an enterprise-grade full-stack banking platform built on the PERN stack: PostgreSQL, Express, React, and Node.js. The architecture is strictly decoupled into a client Single Page Application built with React and Vite, communicating via a RESTful JSON API with an Express backend."

"At the data layer, we use PostgreSQL hosted on Neon, managed through Prisma ORM. Crucially, all financial mutations enforce ACID transactional boundaries, double-entry bookkeeping with immutable ledger entries, and deterministic lock ordering to guarantee zero deadlocks and zero balance drift."

Code Reference: server/server.js, server/app.js, server/prisma/schema.prisma.
Q02 Why did you choose PostgreSQL over NoSQL (like MongoDB) for a banking application?

"Banking software requires strict ACID guarantees (Atomicity, Consistency, Isolation, and Durability). In financial systems, consistency and isolation cannot be compromised for eventual consistency."

"PostgreSQL provides mature relational constraints, foreign keys with cascading rules, write-ahead logging (WAL), row-level write locks, and arbitrary-precision decimal support (Decimal(19, 2)). A document store like MongoDB lacks native multi-table schema constraints and is vulnerable to schema drift and eventual consistency lag during high-concurrency ledger operations."

Code Reference: server/prisma/schema.prisma (PostgreSQL data source and foreign keys).
Q03 Why can't you use standard JavaScript numbers to store and calculate currency?

"JavaScript numbers are 64-bit IEEE 754 binary floating-point numbers. In binary (base-2), base-10 fractions like 0.1 and 0.2 cannot be represented as finite terminating decimals, resulting in infinite repeating binary fractions. Consequently, 0.1 + 0.2 evaluates to 0.30000000000000004."

"In banking, accumulating floating-point drift across millions of transactions breaks double-entry reconciliation. In Swiss Bank, we eliminate this vulnerability by defining all balance and transaction fields in PostgreSQL as Decimal(19, 2) via Prisma, ensuring exact binary-coded decimal precision down to the exact cent."

Code Reference: server/prisma/schema.prisma lines 38, 56.
Q04 How do you prevent double-spending when a user clicks 'Transfer' twice simultaneously?

"We prevent double-spending by encapsulating balance validation, deduction, and ledger insertion within an atomic prisma.$transaction block. Under PostgreSQL's transactional engine, the first transaction acquires an exclusive row-level lock on the sender's account record."

"The second concurrent transaction is blocked at the database level until the first commits. When the second transaction unblocks and reads the balance, it observes the already-debited funds, fails the balance check (fromBalance < numAmount), and throws an ApiException.badRequest('Insufficient balance')."

Code Reference: server/services/accountService.js lines 303–336.
Q05 How do you prevent database deadlocks in concurrent peer-to-peer transfers?

"Cross-transfers (User A transfers to User B while User B transfers to User A) can trigger a deadlock under the Coffman Circular Wait condition if locks are acquired arbitrarily based on sender then receiver."

"In Swiss Bank, we break Coffman's 4th condition (Circular Wait) by implementing deterministic lock acquisition ordering. In accountService.transfer(), we compare the primary keys (fromAcct.id < toAcct.id) and always update the account with the smaller ID first, regardless of transfer direction. Because all concurrent transactions acquire locks according to the exact same total order, wait-for cycles are mathematically impossible."

Code Reference: server/services/accountService.js lines 337–360.
Q06 What is IDOR and how does Swiss Bank protect against it?

"Insecure Direct Object Reference (IDOR) is an access control vulnerability where an application uses client-supplied input to access database objects directly without verifying ownership. For example, an attacker alters fromAccountNumber in DevTools to debit someone else's account."

"In Swiss Bank, client payloads are never trusted for authorization. Our service layer extracts the authenticated user ID strictly from the verified session (req.user.id). Prior to any balance check or mutation, our service asserts: if (fromAcct.ownerId !== owner.id) throw ApiException.forbidden(). Any parameter tampering is immediately rejected with HTTP 403 Forbidden."

Code Reference: server/services/accountService.js lines 64, 77, 115, 314–316.
Q07 What is Step-Up Authentication and how is it implemented?

"Step-Up Authentication is a defense-in-depth pattern where a second factor is requested only when a high-risk action is performed, reducing user friction for low-risk actions."

"In Swiss Bank, transfers below ₹50,000 only require the session and 4-digit PIN. However, if a transfer is ≥ ₹50,000, accountService.transfer() checks if owner.totpEnabled is active. If no totpCode is provided, it throws an ApiException.totpRequired() responding with HTTP 428 Precondition Required. The React client catches this and displays the 2FA modal asking for their Google Authenticator code."

Code Reference: server/services/accountService.js lines 291–299; server/middlewares/errorHandler.js line 30.
Q08 Why do you use express-session with connect-pg-simple instead of in-memory sessions?

"Default in-memory session storage (MemoryStore) causes severe production issues: it leaks memory, cannot scale across multiple horizontal server instances, and loses all active user sessions whenever the Node.js process restarts or deploys."

"By using connect-pg-simple, all session state is persisted inside the PostgreSQL session table. Multiple server instances can share session state, server restarts never disconnect users, and expired sessions are automatically pruned using database timestamps."

Code Reference: server/app.js lines 64–78; server/prisma/schema.prisma lines 99–106.
Q09 What is Double-Entry Bookkeeping and how is it enforced?

"Double-entry bookkeeping is the fundamental accounting principle that money is never created or destroyed out of nothing. Every transaction must consist of at least two equal and opposite entries: a Debit and a Credit."

"In Swiss Bank, when Account A sends ₹5,000 to Account B, our transaction creates two paired immutable records in LedgerEntry sharing the exact same reference code (ref): one DEBIT record for Account A and one CREDIT record for Account B. The net sum across the entire ledger is always zero (∑ Debits = ∑ Credits)."

Q10 Why do you store account numbers as BigInt instead of standard JavaScript Number?

"In JavaScript, standard numbers are 64-bit floats. The maximum integer that can be safely represented without losing precision is Number.MAX_SAFE_INTEGER ($2^{53} - 1 = 9,007,199,254,740,991$)."

"Standard banking account numbers are 12 to 16 digits long. If an account number exceeds 53 bits, standard JavaScript silently truncates or rounds the lowest digits, causing money to be credited to the wrong customer! We use JavaScript's native BigInt and PostgreSQL's BigInt to support arbitrarily large numbers safely."
