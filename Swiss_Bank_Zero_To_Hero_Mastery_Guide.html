Chapter 0: The Universal Technical Dictionary & Glossary

Hard Technical Terms Defined First

Before diving into the code, here is the complete dictionary of every hard technical term used in Swiss Bank. Each term is explained in simple everyday language, followed by its rigorous computer science definition and why it is critical in banking software.

1. ACID Transactions

🐣 Layman Analogy: Buying a drink from a vending machine. You put ₹50 in, the can drops. If the can gets stuck, your ₹50 is refunded. It never keeps your ₹50 while giving you nothing!

👔 CS Definition: The four core properties of reliable relational databases:
• Atomicity: "All or Nothing". All operations in a transaction commit together, or all roll back.
• Consistency: Data must satisfy all schema rules, foreign keys, and constraints before and after.
• Isolation: Concurrent transactions execute without interfering with each other (preventing lost updates).
• Durability: Once committed, data survives power outages and crashes via Write-Ahead Logging (WAL).

🛡️ Why in Banking: When ₹5,000 leaves Account A and enters Account B, both updates must commit together. If the server loses power midway, atomicity guarantees the ₹5,000 never vanishes into thin air.

2. IEEE 754 Floating-Point & Machine Epsilon

🐣 Layman Analogy: Trying to write 1/3 on a paper note. You write 0.333333 and run out of space. Multiplying back by 3 gives 0.999999, not 1.00.

👔 CS Definition: The international standard for representing numbers in computers using 64 bits: 1 sign bit, 11 exponent bits, and 52 fraction/mantissa bits. In base 2, fractions like 0.1 and 0.2 repeat infinitely ($0.000110011..._2$). Truncating at 53 bits introduces machine epsilon ($epsilon approx 2.22 imes 10^{-16}$) error, causing 0.1 + 0.2 === 0.30000000000000004.

🛡️ Why in Banking: Accumulating float rounding errors across millions of ledger entries causes ledger reconciliation to fail audits. Swiss Bank prevents this by using PostgreSQL Decimal(19, 2) arbitrary-precision storage.

3. Binary Coded Decimal (BCD) / Decimal(19, 2)

🐣 Layman Analogy: An old-fashioned mechanical odometer in a car where each wheel has digits 0 through 9 stamped in metal. Every digit is exact and physical.

👔 CS Definition: A class of binary encodings of decimal numbers where each decimal digit is represented by a fixed number of binary bits. In PostgreSQL, NUMERIC/DECIMAL stores digits in base-10,000 chunks without binary float approximations.

🛡️ Why in Banking: Guarantees mathematical exactness down to the exact cent, with 17 digits before the decimal point and 2 digits after.

4. BigInt & Number.MAX_SAFE_INTEGER

🐣 Layman Analogy: A measuring tape that only goes up to 9 meters. If you try to measure a 12-meter room, the tape snaps and gives you a fake number!

👔 CS Definition: In JavaScript, standard numbers are 64-bit floats. The highest integer that can be represented safely without losing precision is $2^{53} - 1 = 9,007,199,254,740,991$ (16 digits). Above this, numbers are rounded to the nearest even number. BigInt is a native JavaScript type that supports arbitrarily large integers without rounding.

🛡️ Why in Banking: 12-digit to 16-digit bank account numbers (e.g. 102938475612) can exceed safe limits in calculations. Using BigInt guarantees every single digit of the account number is perfectly preserved.

5. Row-Level Write Locks (SELECT ... FOR UPDATE)

🐣 Layman Analogy: The "Occupied" lock on an airplane bathroom door. While you are inside, no one else can open the door. They must wait outside until you finish and unlock it.

👔 CS Definition: A concurrency control mechanism where the database engine grants an exclusive write lock on a specific table row to a single transaction. All other transactions attempting to read or update that same row are blocked until the lock-holding transaction issues a COMMIT or ROLLBACK.

🛡️ Why in Banking: Stops double-spending! If you click "Transfer ₹1,000" twice in the same millisecond from two tabs, the lock forces Request #2 to wait until Request #1 debits the balance.

6. Deadlocks & Coffman Conditions

🐣 Layman Analogy: Two cars arriving at a single-lane bridge from opposite sides at the exact same second. Neither driver will reverse, so both sit there honking forever.

👔 CS Definition: A state where two or more processes are unable to proceed because each is waiting for a resource held by the other. By Coffman's Theorem (1971), deadlocks occur if and only if 4 conditions hold simultaneously: Mutual Exclusion, Hold and Wait, No Preemption, and Circular Wait.

🛡️ Why in Banking: If Alice sends money to Bob (locks Alice, requests Bob) while Bob sends to Alice (locks Bob, requests Alice), both freeze. Swiss Bank breaks Circular Wait by using Deterministic Lock Ordering (updating the lower account ID first).

7. Insecure Direct Object Reference (IDOR / OWASP A01)

🐣 Layman Analogy: You check into hotel room 101, but you tell the clerk: "Please open room 205 for me." If the clerk opens room 205 without checking if you rented it, that is IDOR.

👔 CS Definition: A vulnerability categorized under OWASP Top 10 A01 (Broken Access Control) where an application takes client-supplied object IDs (like account numbers or primary keys) and queries or updates the database without verifying whether the authenticated user has authorization rights over that object.

🛡️ Why in Banking: A hacker could open DevTools and change fromAccountNumber: 1002 in the JSON payload to drain another customer's account. Swiss Bank checks if (fromAcct.ownerId !== req.user.id) throw ApiException.forbidden() on every endpoint!

8. Step-Up Authentication (RFC 428 Precondition Required)

🐣 Layman Analogy: Entering an office building with a basic visitor badge is fine for getting a coffee in the lobby. But to enter the high-security server vault, you must also provide your fingerprint.

👔 CS Definition: A security architecture pattern where users authenticate once with basic credentials (session cookie/PIN) for low-risk actions, but the system dynamically demands elevated verification (a second factor like TOTP) before executing high-risk, irreversible operations.

🛡️ Why in Banking: Transfers below ₹50,000 only need a PIN. But any transfer ≥ ₹50,000 triggers Step-Up 2FA, returning HTTP 428 Precondition Required and demanding a 6-digit Google Authenticator code.

9. RFC 6238 TOTP (Time-Based One-Time Password)

🐣 Layman Analogy: You and a friend agree on a secret math puzzle and both look at the clock. Every 30 seconds, you both calculate the puzzle using the current time. Since both of your clocks read the same time, you both get the exact same 6-digit answer without talking to each other!

👔 CS Definition: An algorithm that computes a one-time passcode from a shared secret key $K$ and current time $T$. The time counter $C = lfloor T / 30 floor$ is hashed with the key using HMAC-SHA1: $ ext{HMAC} = ext{HMAC-SHA1}(K, C)$. Dynamic truncation extracts a 6-digit integer.

🛡️ Why in Banking: Works even when the customer's phone has no internet (Airplane Mode) because time and the secret key are identical on both devices!

10. BCrypt Hashing & Salt Rounds

🐣 Layman Analogy: A combination lock that takes 10 seconds to test each key. If a thief tries to guess millions of combinations, it would take them 1,000 years!

👔 CS Definition: A password-hashing function based on the Blowfish cipher that incorporates a salt to protect against rainbow table attacks and an adaptive work factor (cost parameter). In Swiss Bank, 10 salt rounds ($2^{10} = 1024$ iterations) are used, making brute-force GPU attacks computationally infeasible.

🛡️ Why in Banking: If a hacker steals the database, they cannot reverse the hashes into plain passwords.

11. Double-Entry Bookkeeping

🐣 Layman Analogy: If you move ₹500 from your left pocket to your right pocket, your left pocket loses ₹500 and your right pocket gains ₹500. Total money in your pants remains exactly the same!

👔 CS Definition: The 500-year-old accounting standard mandating that every financial transaction must be recorded in at least two accounts, where the total debits must equal the total credits: $sum ext{Debits} - sum ext{Credits} = 0$.

🛡️ Why in Banking: Money is never created or destroyed out of thin air. Swiss Bank writes two immutable ledger rows (DEBIT and CREDIT) under the same transaction reference for every single transfer.

12. Write-Ahead Logging (WAL)

🐣 Layman Analogy: Writing down your grocery list in a notebook *before* driving to the store. If you drop the eggs on the way, you can read your notebook to see what was supposed to happen.

👔 CS Definition: A standard database technique where data modifications are written sequentially to a durable log file on disk *before* the changes are applied to the database data pages in memory.

🛡️ Why in Banking: If the database crashes or loses electricity mid-transaction, PostgreSQL reads the WAL upon reboot and either rolls back uncommitted steps or replays committed steps, guaranteeing zero data loss.

01

Trap 1: The Floating-Point Rounding Trap & Penny Drift

IEEE 754 Binary Floating-Point vs Arbitrary-Precision Decimal Storage

Penny Leakage
🐣 Layman Language
The 1/3 Paper Analogy
Try writing 1/3 on a small note. You write 0.333333 and run out of space. Multiply it back by 3: you get 0.999999, not 1.00! That 0.000001 was lost because paper is finite.

In computers, numbers are stored in base-2 (binary). Just as 1/3 cannot be written finitely in decimal, 0.1 and 0.2 cannot be written finitely in binary. In JavaScript, 0.1 + 0.2 === 0.30000000000000004. Over millions of transactions, tiny fractions of pennies leak out or appear out of nowhere, breaking accounting audits.
👔 Technical Interview Language
IEEE 754 64-Bit Float vs Decimal(19, 2)
Standard JavaScript uses 64-bit binary floating-point numbers. In base 2, fractions only terminate if the denominator is a power of 2 ($2^k$). Because $0.1 = 1/10 = 1/(2 imes 5)$, its binary representation is an infinite repeating fraction ($0.000110011..._2$). Truncating at 53 bits introduces machine epsilon ($epsilon approx 2.22 imes 10^{-16}$) error.

Swiss Bank Fix: In schema.prisma (lines 38, 56), balances and ledger amounts are configured as @db.Decimal(19, 2). PostgreSQL stores these as exact Binary Coded Decimals without binary floating-point approximation.
02

Trap 2: The Double-Spending Race Condition

Time-of-Check to Time-of-Use (TOCTOU) & Lost Updates

Double Withdrawal
🐣 Layman Language
Two Friends at Two ATMs Simultaneously
You have ₹1,000 in your account. You give two debit cards to two friends at two separate ATMs. At the exact same second (12:00:00.000), both press "Withdraw ₹1,000".

If the bank software checks ATM #1 (balance ₹1,000 — approved!) and ATM #2 (balance ₹1,000 — approved!), both ATMs spit out cash. You withdrew ₹2,000 from a ₹1,000 balance!
👔 Technical Interview Language
Atomic Transactions & Row-Level Write Locks
This is a classic Time-of-Check to Time-of-Use (TOCTOU) race condition.

Swiss Bank Fix: In accountService.js (lines 303–384), all balance checking, deduction, and ledger creation are executed inside an atomic prisma.$transaction(async (tx) => { ... }). PostgreSQL acquires an exclusive row write lock on the sender's account. Any concurrent transaction is forced to wait until the first commits, at which point it reads the depleted balance and fails the sufficiency check (fromBalance < numAmount).
03

Trap 3: The Deadlock Trap in Peer-to-Peer Cross-Transfers

Coffman Conditions, Circular Wait & Deterministic Lock Ordering

System Freezing
🐣 Layman Language
The Narrow Doorway Stalemate
Alice and Bob meet in a narrow doorway. Alice says: "I will not step back until you step forward." Bob says: "I will not step back until you step forward." Both stand there frozen forever.

In a bank: Alice sends to Bob (locks Alice, waits for Bob). At the same millisecond, Bob sends to Alice (locks Bob, waits for Alice). Both wait on each other until the database crashes!
👔 Technical Interview Language
Deterministic Global Total Order (Havender's Principle)
By Coffman's Theorem (1971), deadlocks require Circular Wait ($T_1 o R_2 o T_2 o R_1$).

Swiss Bank Fix: In accountService.js (lines 337–360), we enforce deterministic lock acquisition ordering by comparing account primary keys:
if (fromAcct.id < toAcct.id) { update(fromAcct); update(toAcct); } else { update(toAcct); update(fromAcct); }.
Because every transaction in the system acquires locks in the exact same numerical order, wait-for cycles are mathematically impossible!

ACID Atomicity & Write-Ahead Logging (WAL) Rollbacks

Money Vanishing
🐣 Layman Language
The Power Cut at Checkout
You hand ₹50,000 cash to a store clerk. The clerk takes the money. But before handing you the television, lightning strikes, the power cuts out, and store alarms force everyone outside. You lost ₹50,000 and have no television!

📖 Hard Technical Terms in this File

💡 Why it is used: To establish an impenetrable defense-in-depth security perimeter before any business code runs. It prevents clickjacking, enforces CORS origin whitelisting, unpacks JSON payloads, and validates sessions against PostgreSQL.
⚙️ How it is implemented: Chains Express middleware in strict sequential order: Helmet → CORS → Body Parsers → PostgreSQL Session → Routes → Error Handler.
🏛️ What it does in Swiss Bank: Protects all banking endpoints, manages user session continuity across restarts, and registers API sub-routers.

const HTTP_STATUS_NAMES = {
  400: 'Bad Request',
  401: 'Unauthorized',
  403: 'Forbidden',
  404: 'Not Found',
  409: 'Conflict',
  428: 'Precondition Required',
  500: 'Internal Server Error',
};

export function errorHandler(err, req, res, next) {
  const status = err.status || 500;
  const errorName = HTTP_STATUS_NAMES[status] || (status >= 500 ? 'Internal Server Error' : 'Error');
  const message = err.message || 'Unexpected error';

  const responseBody = {
    timestamp: new Date().toISOString(),
    status,
    error: errorName,
    message,
  };

  if (err.code) {
    responseBody.code = err.code;
  }

  if (err.fieldErrors) {
    responseBody.fieldErrors = err.fieldErrors;
  }

  if (status >= 500) {
    console.error('[Unhandled Error]', err);
  }

  res.status(status).json(responseBody);
}

import bcrypt from 'bcryptjs';
import prisma from '../config/prisma.js';
import { ApiException } from '../middlewares/errorHandler.js';
import totpService from '../services/totpService.js';
import userService, { toUserResponse } from '../services/userService.js';

const MAX_MFA_ATTEMPTS = 5;

export const authController = {
  async register(req, res, next) {
    try {
      const { fullName, email, password, phone, dateOfBirth, panNumber, address } = req.body;
      if (!fullName || !email || !password) {
        throw ApiException.badRequest('Full name, email, and password are required');
      }

      const user = await userService.register({
        fullName,
        email,
        password,
        phone,
        dateOfBirth,
        panNumber,
        address,
      });

      res.status(201).json(toUserResponse(user));
    } catch (err) {
      next(err);
    }
  },

  async login(req, res, next) {
    try {
      const { email, password } = req.body;
      if (!email || !password) {
        return next(ApiException.badRequest('Email and password are required'));
      }

      const user = await prisma.user.findUnique({
        where: { email: email.trim().toLowerCase() },
      });

      if (!user) {
        return next(new ApiException(401, 'Invalid email or password'));
      }

      const matches = await bcrypt.compare(password, user.passwordHash);
      if (!matches) {
        return next(new ApiException(401, 'Invalid email or password'));
      }

      if (user.totpEnabled) {
        req.session.mfaUserId = user.id;
        req.session.mfaAttempts = 0;
        return res.json({
          mfaRequired: true,
          fullName: user.fullName,
          user: null,
        });
      }

      req.session.userId = user.id;
      res.json({
        mfaRequired: false,
        fullName: null,
        user: toUserResponse(user),
      });
    } catch (err) {
      next(err);
    }
  },

  async verifyLoginCode(req, res, next) {
    try {
      const { code } = req.body;
      const mfaUserId = req.session ? req.session.mfaUserId : null;

      if (!mfaUserId) {
        throw ApiException.forbidden('No sign-in in progress -- please sign in again');
      }

      const user = await prisma.user.findUnique({
        where: { id: mfaUserId },
      });

      if (!user || !user.totpSecret) {
        throw ApiException.forbidden('Invalid session state -- please sign in again');
      }

      if (!totpService.verify(user.totpSecret, code)) {
        const attempts = (req.session.mfaAttempts || 0) + 1;
        if (attempts >= MAX_MFA_ATTEMPTS) {
          req.session.destroy(() => {});
          throw ApiException.forbidden('Too many incorrect codes -- please sign in again');
        }
        req.session.mfaAttempts = attempts;
        throw ApiException.totpInvalid(`Incorrect code -- ${MAX_MFA_ATTEMPTS - attempts} attempts left`);
      }

      delete req.session.mfaUserId;
      delete req.session.mfaAttempts;
      req.session.userId = user.id;

      res.json({
        mfaRequired: false,
        fullName: null,
        user: toUserResponse(user),
      });
    } catch (err) {
      next(err);
    }
  },

  async me(req, res, next) {
    try {
      res.json(toUserResponse(req.user));
    } catch (err) {
      next(err);
    }
  },

  async changePassword(req, res, next) {
    try {
      const { currentPassword, newPassword } = req.body;
      if (!currentPassword || !newPassword) {
        throw ApiException.badRequest('Current password and new password are required');
      }
      await userService.changePassword(req.user, currentPassword, newPassword);
      res.status(204).send();
    } catch (err) {
      next(err);
    }
  },

  async logout(req, res, next) {
    try {
      if (req.session) {
        req.session.destroy(() => {
          res.clearCookie('connect.sid');
          res.status(204).send();
        });
      } else {
        res.status(204).send();
      }
    } catch (err) {
      next(err);
    }
  },
};

import bcrypt from 'bcryptjs';
import prisma from '../config/prisma.js';
import { ApiException } from '../middlewares/errorHandler.js';

export const userService = {
  async register({ fullName, email, password, phone, dateOfBirth, panNumber, address }) {
    const normalizedEmail = email.trim().toLowerCase();
    
    const existing = await prisma.user.findUnique({
      where: { email: normalizedEmail },
    });

    if (existing) {
      throw ApiException.conflict('An account already exists for that email');
    }

    if (dateOfBirth) {
      const dob = new Date(dateOfBirth);
      const minAgeDate = new Date();
      minAgeDate.setFullYear(minAgeDate.getFullYear() - 18);
      if (dob > minAgeDate) {
        throw ApiException.badRequest('You must be at least 18 years old to open an account');
      }
    }

    const passwordHash = await bcrypt.hash(password, 10);

    return prisma.user.create({
      data: {
        fullName: fullName.trim(),
        email: normalizedEmail,
        passwordHash,
        phone: phone ? phone.trim() : null,
        dateOfBirth: dateOfBirth ? new Date(dateOfBirth) : null,
        panNumber: panNumber ? panNumber.trim().toUpperCase() : null,
        address: address ? address.trim() : null,
        role: 'USER',
      },
    });
  },

  async byEmail(email) {
    const user = await prisma.user.findUnique({
      where: { email: email.trim().toLowerCase() },
    });
    if (!user) {
      throw ApiException.notFound('User not found');
    }
    return user;
  },

  async byId(id) {
    const user = await prisma.user.findUnique({
      where: { id: Number(id) },
    });
    if (!user) {
      throw ApiException.notFound('User not found');
    }
    return user;
  },

  async changePassword(user, currentPassword, newPassword) {
    const matches = await bcrypt.compare(currentPassword, user.passwordHash);
    if (!matches) {
      throw ApiException.forbidden('Current password is incorrect');
    }
    const newHash = await bcrypt.hash(newPassword, 10);
    return prisma.user.update({
      where: { id: user.id },
      data: { passwordHash: newHash },
    });
  },

  async allUsers() {
    return prisma.user.findMany({
      orderBy: { createdAt: 'desc' },
      include: {
        accounts: {
          orderBy: { createdAt: 'desc' },
        },
      },
    });
  },
};

    fullName: user.fullName,

}

  async transfer(owner, { fromAccountNumber, toAccountNumber, amount, pin, totpCode }) {
    const fromNum = BigInt(fromAccountNumber);
    const toNum = BigInt(toAccountNumber);
    const numAmount = Number(amount);

    if (fromNum === toNum) {
      throw ApiException.badRequest('Cannot transfer to the same account');
    }
    if (!numAmount || numAmount <= 0) {
      throw ApiException.badRequest('Transfer amount must be positive');
    }

    // High value transfer check (>= 50,000)
    if (owner.totpEnabled && numAmount >= HIGH_VALUE_THRESHOLD) {
      if (!totpCode || totpCode.trim() === '') {
        throw ApiException.totpRequired(`This transfer is above ₹${HIGH_VALUE_THRESHOLD.toLocaleString('en-IN')} — enter your 2FA code to confirm`);
      }
      if (!totpService.verify(owner.totpSecret, totpCode.trim())) {
        throw ApiException.totpInvalid('Incorrect 2FA code');
      }
    }

    const ref = newReference();

    const result = await prisma.$transaction(async (tx) => {
      const fromAcct = await tx.account.findUnique({ where: { accountNumber: fromNum } });
      const toAcct = await tx.account.findUnique({ where: { accountNumber: toNum } });

      if (!fromAcct) {
        throw ApiException.notFound(`Account #${fromAccountNumber} not found`);
      }
      if (!toAcct) {
        throw ApiException.notFound(`Account #${toAccountNumber} not found`);
      }

      if (fromAcct.ownerId !== owner.id) {
        throw ApiException.forbidden("You don't own the source account");
      }
      if (fromAcct.frozen) {
        throw ApiException.forbidden(`Account #${fromAccountNumber} is frozen — contact support`);
      }
      if (toAcct.frozen) {
        throw ApiException.forbidden(`Recipient Account #${toAccountNumber} is frozen — contact support`);
      }

      const matches = await bcrypt.compare(pin, fromAcct.pinHash);
      if (!matches) {
        throw ApiException.forbidden('Invalid security PIN');
      }

      const fromBalance = Number(fromAcct.balance);
      if (fromBalance < numAmount) {
        throw ApiException.badRequest('Insufficient balance');
      }

      const updatedFromBalance = fromBalance - numAmount;
      const updatedToBalance = Number(toAcct.balance) + numAmount;

      // Deterministic Lock Acquisition Ordering (Deadlock Prevention):
      // Always update the lower Account ID first, regardless of whether it is sender or receiver.
      // This eliminates the Coffman "circular wait" condition and guarantees zero deadlocks under concurrent cross-transfers.
      let updatedFrom;
      if (fromAcct.id < toAcct.id) {
        updatedFrom = await tx.account.update({
          where: { id: fromAcct.id },
          data: { balance: updatedFromBalance },
        });
        await tx.account.update({
          where: { id: toAcct.id },
          data: { balance: updatedToBalance },
        });
      } else {
        await tx.account.update({
          where: { id: toAcct.id },
          data: { balance: updatedToBalance },
        });
        updatedFrom = await tx.account.update({
          where: { id: fromAcct.id },
          data: { balance: updatedFromBalance },
        });
      }

      // Write two ledger entries (Double-entry) under same reference
      await tx.ledgerEntry.create({
        data: {
          accountId: fromAcct.id,
          type: 'DEBIT',
          amount: numAmount,
          balanceAfter: updatedFromBalance,
          description: `Transfer to #${toAcct.accountNumber}`,
          reference: ref,
        },
      });

      await tx.ledgerEntry.create({
        data: {
          accountId: toAcct.id,
          type: 'CREDIT',
          amount: numAmount,
          balanceAfter: updatedToBalance,
          description: `Transfer from #${fromAcct.accountNumber}`,
          reference: ref,
        },
      });

      return updatedFrom;
    });

    return toAccountResponse(result);
  },

export function toCardResponse(c, account) {
  const acct = account || c.account;
  return {
    accountNumber: Number(acct.accountNumber),
    holderName: acct.holderName,
    network: c.network,
    expiryMonth: c.expiryMonth,
    expiryYear: c.expiryYear,
    frozen: c.frozen,
    contactlessEnabled: c.contactlessEnabled,
    onlineEnabled: c.onlineEnabled,
    dailyLimit: Number(c.dailyLimit),

export const cardService = {
  async getOrCreate(account) {
    let card = await prisma.card.findUnique({
      where: { accountId: account.id },
      include: { account: true },
    });

    if (!card) {
      const now = new Date();
      const expiryYear = now.getFullYear() + 4;
      const expiryMonth = now.getMonth() + 1;

      card = await prisma.card.create({
        data: {
          accountId: account.id,
          network: 'VISA',
          expiryMonth,
          expiryYear,
          frozen: false,
          contactlessEnabled: true,
          onlineEnabled: true,
          dailyLimit: 25000.0,
        },
        include: { account: true },
      });
    }

    return card;
  },

  async mine(owner) {
    const ownedAccounts = await prisma.account.findMany({
      where: { ownerId: owner.id },
      orderBy: { createdAt: 'desc' },
    });

    const cards = await Promise.all(
      ownedAccounts.map((acct) => this.getOrCreate(acct))
    );

    return cards.map((c) => toCardResponse(c));
  },

  async getOrCreateOwned(owner, accountNumber) {
    const acct = await prisma.account.findUnique({
      where: { accountNumber: BigInt(accountNumber) },
    });
    if (!acct) {
      throw ApiException.notFound('Account not found');
    }
    if (acct.ownerId !== owner.id) {
      throw ApiException.forbidden("You don't own this account");
    }
    return this.getOrCreate(acct);
  },

  async update(owner, accountNumber, { frozen, contactlessEnabled, onlineEnabled }) {
    const card = await this.getOrCreateOwned(owner, accountNumber);

    const updateData = {};
    if (frozen !== undefined) updateData.frozen = Boolean(frozen);
    if (contactlessEnabled !== undefined) updateData.contactlessEnabled = Boolean(contactlessEnabled);
    if (onlineEnabled !== undefined) updateData.onlineEnabled = Boolean(onlineEnabled);

    const updated = await prisma.card.update({
      where: { id: card.id },
      data: updateData,
      include: { account: true },
    });

    return toCardResponse(updated);
  },

  async requestReplacement(owner, accountNumber) {
    const card = await this.getOrCreateOwned(owner, accountNumber);

    const updated = await prisma.card.update({
      where: { id: card.id },
      data: { replacementRequestedAt: new Date() },
      include: { account: true },
    });

    return toCardResponse(updated);
  },
};

  async pay(owner, { accountNumber, category, consumer, amount, pin }) {

      throw ApiException.badRequest('Missing required bill payment parameters');
    }

    const { reference } = await accountService.debitInternal(
      owner,
      accountNumber,
      amount,
      pin,
      `${category} · ${consumer}`

      include: { account: true },

    const skip = (Number(page) || 0) * take;

    const [totalElements, payments] = await Promise.all([
      prisma.billPayment.count({ where: { ownerId: owner.id } }),
      prisma.billPayment.findMany({
        where: { ownerId: owner.id },
        include: { account: true },
        orderBy: { createdAt: 'desc' },
        skip,
        take,
      }),
    ]);

    const totalPages = Math.ceil(totalElements / take) || (totalElements === 0 ? 0 : 1);
    const pageNum = Number(page) || 0;

    return {
      content: payments.map(toBillPaymentResponse),
      page: pageNum,
      size: take,
      totalElements,
      totalPages,
      first: pageNum === 0,
      last: pageNum >= totalPages - 1 || totalPages === 0,
    };
  },

  },

      where: { ownerId: owner.id },
      orderBy: { createdAt: 'desc' },
    });

      where: { id: Number(id) },

const API_BASE = import.meta.env.VITE_API_URL || '';

export async function api(path, options = {}) {
  const url = path.startsWith('http') ? path : `${API_BASE}${path}`;
  const headers = {
    'Content-Type': 'application/json',
    ...(options.headers || {}),
  };

  try {
    const res = await fetch(url, {
      credentials: 'include',
      headers,
      ...options,
    });

    if (res.status === 401) {
      if (window.location.pathname !== '/login') {
        window.location.href = '/login';
      }
      throw { status: 401, message: 'Not authenticated' };
    }

    if (res.status === 204) {
      return null;
    }

    const contentType = res.headers.get('content-type') || '';
    if (contentType.includes('text/csv')) {
      return await res.blob();
    }

    const text = await res.text();
    let body = null;
    if (text) {
      try {
        body = JSON.parse(text);
      } catch {
        body = text;
      }
    }

    if (!res.ok) {
      throw {
        status: res.status,
        body,
        message: (body && body.message) || `Request failed (${res.status})`,
        fieldErrors: (body && body.fieldErrors) || null,
        code: (body && body.code) || null,
      };
    }

    return body;
  } catch (err) {
    if (err.status) throw err;
    throw {
      status: 0,
      message: "Couldn't reach the server — check your connection.",
      body: null,
    };
  }
}

const ThemeContext = createContext();

export function ThemeProvider({ children }) {
  const [theme, setThemeState] = useState(() => {
    return localStorage.getItem('theme') || 'system';
  });

  const applyTheme = (t) => {
    const root = document.documentElement;
    if (t === 'system') {
      const prefersDark = window.matchMedia('(prefers-color-scheme: dark)').matches;
      if (prefersDark) {
        root.setAttribute('data-theme', 'dark');
      } else {
        root.removeAttribute('data-theme');
      }
    } else if (t === 'dark') {
      root.setAttribute('data-theme', 'dark');
    } else {
      root.removeAttribute('data-theme');
    }
  };

  useEffect(() => {
    applyTheme(theme);
    localStorage.setItem('theme', theme);

    const mql = window.matchMedia('(prefers-color-scheme: dark)');
    const onChange = () => {
      if (theme === 'system') {
        applyTheme('system');
      }
    };
    mql.addEventListener('change', onChange);
    return () => mql.removeEventListener('change', onChange);
  }, [theme]);

  const setTheme = (t) => {
    setThemeState(t);
  };

  return (
    <ThemeContext.Provider value={{ theme, setTheme }}>
      {children}
    </ThemeContext.Provider>
  );
}

  const toast = useToast();
  const navigate = useNavigate();

  const [users, setUsers] = useState([]);
  const [tickets, setTickets] = useState([]);
  const [loading, setLoading] = useState(true);

  const loadAdminData = async () => {
    try {
      const [usersData, ticketsData] = await Promise.all([
        api('/api/admin/users'),
        api('/api/admin/tickets'),
      ]);
      setUsers(usersData || []);
      setTickets(ticketsData || []);
    } catch (err) {
      if (err.status === 403) {
        toast('Admin privileges required', 'error');
        navigate('/');
      } else {
        toast('Failed to load admin telemetry', 'error');
      }
    } finally {
      setLoading(false);
    }
  };

  useEffect(() => {
    if (user && user.role !== 'ADMIN') {
      toast('Access restricted to Bank Administrators', 'error');
      navigate('/');
    } else {
      loadAdminData();
    }
  }, [user]);

  const handleToggleFreeze = async (accountNumber, currentlyFrozen) => {
    try {
      if (currentlyFrozen) {
        await api(`/api/admin/accounts/${accountNumber}/unfreeze`, { method: 'POST' });
        toast(`Account #${accountNumber} unfrozen`);
      } else {
        await api(`/api/admin/accounts/${accountNumber}/freeze`, { method: 'POST' });
        toast(`Account #${accountNumber} frozen`);
      }
      loadAdminData();
    } catch (err) {
      toast(err.message || 'Failed to toggle account status', 'error');
    }

      await api(`/api/admin/tickets/${id}/close`, { method: 'POST' });

      loadAdminData();
    } catch (err) {
      toast(err.message || 'Failed to close ticket', 'error');
    }

Chapter 8: Master 35-Question Senior FinTech Interview Defense

Verbatim Defense Scripts

The exhaustive cheatsheet of questions asked by FAANG, hedge funds, and top fintech engineering interviewers. Click on any question to expand the verbatim answer script.

Q01 Can you walk me through the high-level architecture of Swiss Bank?

"Swiss Bank is built on a 4-tier enterprise PERN architecture: a React 18 Single Page Application hosted on Vercel Edge CDN, communicating via HTTPS REST with an Express 4.x backend deployed on Render Web Services, backed by a serverless PostgreSQL instance on Neon Cloud. All state mutations pass through Helmet security armor, CORS origin validation, and PostgreSQL session stores before reaching domain controllers. Financial transactions run inside Prisma transactions using row-level exclusive write locks, deterministic deadlock prevention, and immutable double-entry bookkeeping."

Q02 Why did you choose PostgreSQL over MongoDB for a banking system?

"Banking systems demand strict ACID guarantees, normalized relational schemas, and serializable constraints. MongoDB is document-oriented and historically favors eventual consistency and flexible schemas. PostgreSQL offers native arbitrary-precision Decimal(19, 2) arithmetic, transactional DDL, row-level locking (SELECT FOR UPDATE), foreign key referential integrity with cascade controls, and Write-Ahead Logging (WAL). In financial ledgers, preventing schema drift and phantom records is paramount."

Q03 What is the floating-point rounding trap in financial systems, and how do you prevent it?

"JavaScript and most runtimes represent numbers using IEEE 754 64-bit binary floating-point. In binary base-2, numbers like 0.1 and 0.2 cannot be represented finitely (repeating fractions), causing 0.1 + 0.2 === 0.30000000000000004. Over millions of transactions, accumulated rounding error breaks ledger reconciliation. Swiss Bank eliminates floating-point drift by configuring balances and transfer amounts as PostgreSQL @db.Decimal(19, 2), storing values in base-10,000 arbitrary-precision format and converting to strings/integers at the API boundary."

Q04 How do you prevent double-spending race conditions during concurrent money transfers?

"If a user with ₹1,000 double-clicks 'Transfer ₹1,000' in the same millisecond, two concurrent requests could read balance = ₹1,000 and both approve the transfer. We prevent this using database row-level exclusive write locks (SELECT ... FOR UPDATE) inside prisma.$transaction. The first transaction acquires an exclusive lock on the sender's account row; the second transaction is blocked and forced to wait until the first completes. When the second transaction unblocks, it reads the updated balance (₹0) and throws an Insufficient Funds exception."

Q05 What is a database deadlock, Coffman's conditions, and how does Swiss Bank eliminate deadlocks?

"A deadlock occurs when Transaction A locks Account 1 and waits for Account 2, while Transaction B locks Account 2 and waits for Account 1. Both freeze indefinitely until the database engine terminates one with an error. According to Coffman's conditions, deadlocks require Mutual Exclusion, Hold and Wait, No Preemption, and Circular Wait. Swiss Bank mathematically breaks the Circular Wait condition by enforcing deterministic lock acquisition ordering: before acquiring row locks, we sort account IDs ascendingly (min(A, B) first, then max(A, B)). Both transactions lock in the exact same physical order, rendering circular wait impossible."

Q06 What is double-entry bookkeeping, and how is it implemented in your ledger?

"Double-entry bookkeeping is the fundamental accounting principle that every financial transaction must affect at least two accounts with equal and opposite entries: a debit and a credit. In Swiss Bank, every transfer creates two LedgerEntry rows sharing a unique reference UUID (ref): a DEBIT entry on the sender's account and a CREDIT entry on the recipient's account. This guarantees mathematical conservation: the sum of all debits minus credits across the institution is strictly zero."

Q07 How do you prevent Insecure Direct Object References (IDOR) across account and card endpoints?

"An IDOR occurs when an application exposes a database key (like account ID or account number) and fails to verify that the requesting user owns that entity. In Swiss Bank, every service method (accountService, cardService, beneficiaryService) validates that the caller's session ID matches the resource's ownerId: if (account.ownerId !== req.user.id) throw ApiException.forbidden('You do not own this account'). Even if an attacker guesses another user's 10-digit account number, their request is immediately rejected."

Q08 How does Step-Up 2FA work, and why not just require 2FA on login?

"Requiring 2FA solely on login leaves users vulnerable to session hijacking (e.g. coffee shop Wi-Fi session theft or an unlocked laptop). Step-Up 2FA requires the user to re-authenticate using their 6-digit TOTP token specifically when executing high-value or destructive actions (such as transfers exceeding ₹10,000 or updating daily card limits). If the 2FA code is absent or invalid, the backend halts execution with HTTP 428 Precondition Required or 400 Bad Request."

Q09 Walk me through the mathematical implementation of RFC 6238 TOTP.

"TOTP (Time-Based One-Time Password) uses a shared secret key K (Base32 encoded) and the current Unix time T. It calculates the time-step counter C = floor((CurrentTime - T0) / 30). It then computes an HMAC-SHA1 hash: H = HMAC-SHA1(K, C). Dynamic truncation extracts a 4-byte string from H based on the low-order 4 bits of the last byte. Taking the extracted 31-bit integer modulo 10^6 yields a 6-digit number. Swiss Bank validates codes within a ±1 step window to accommodate device clock drift."

Q10 Why did you choose server-side sessions over JWTs for authentication?

"In financial applications, immediate revocation capability is a non-negotiable security requirement. If an account is frozen due to suspected fraud, or if a user reports their device stolen, all active sessions must be terminated instantly. JWTs are stateless and self-contained; revoking a JWT requires maintaining a centralized token blacklist, which defeats the stateless benefit of JWTs. Swiss Bank uses express-session backed by PostgreSQL (connect-pg-simple), allowing instant session invalidation with a single database DELETE."

Q11 Explain your cookie security flags: HttpOnly, Secure, and SameSite.

"In app.js, session cookies are configured with: (1) httpOnly: true, which prevents client-side JavaScript from accessing document.cookie, completely mitigating XSS cookie theft; (2) secure: true (in production), ensuring cookies are only transmitted over TLS encrypted HTTPS connections; (3) sameSite: 'none' (with secure: true) in production, allowing the decoupled Vercel frontend to include session cookies in cross-origin fetch requests to the Render backend."

Q12 How do you handle cross-origin cookies between Vercel (client) and Render (server)?

"Because Vercel and Render reside on distinct domains (e.g., swiss-bank.vercel.app and swiss-bank-api.onrender.com), browsers classify API calls as third-party cross-site requests. To make cookies persist: the Express CORS middleware must explicitly whitelist the client origin (origin: process.env.CLIENT_URL, credentials: true), the session cookie must specify sameSite: 'none' and secure: true, and the frontend fetch client (api.js) must explicitly pass credentials: 'include'."

Q13 What is CSV Formula Injection (CWE-1236), and how did you patch it in statement export?

"CSV Formula Injection occurs when untrusted user input (such as transaction transfer descriptions) begins with executable spreadsheet formula characters: =, +, -, or @. When a compliance officer opens the exported CSV in Microsoft Excel or LibreOffice, the spreadsheet executes the payload (e.g., =CMD|' /C calc'!A0 or data exfiltration via DDE). Swiss Bank sanitizes every string field before writing CSV rows: if a string begins with any of those characters, we prefix it with a single quote ('), instructing the spreadsheet engine to treat it strictly as literal text."

Q14 How does connection pooling work in PostgreSQL, and why do you use both pg.Pool and Prisma Client?

"PostgreSQL forks a dedicated operating system process for each client connection, making connection creation resource-intensive (TCP and TLS handshakes, process allocation). A connection pool maintains an active pool of open connections, reusing them across incoming HTTP requests. We use pg.Pool specifically for connect-pg-simple to manage the high-frequency session table queries, while Prisma Client maintains its own internal Rust-based connection pool for application queries, optimizing resource usage."

Q15 Why is app.set('trust proxy', 1) required when deploying on cloud platforms like Render or AWS?

"Cloud platforms deploy applications behind reverse proxies and load balancers that terminate SSL/TLS at the edge and forward plain HTTP to the container. Without app.set('trust proxy', 1), Express sees the incoming connection as insecure HTTP (req.secure === false) and refuses to set session cookies marked with the secure: true flag. Trusting the proxy enables Express to parse the X-Forwarded-Proto: https header."

Q16 How do you prevent password brute-force and timing attacks during authentication?

"In userService.js, passwords are authenticated using bcrypt.compare(), which executes in constant time to prevent side-channel timing analysis attacks. Furthermore, in authController.js, we track MFA failure attempts on the session object: after 5 consecutive failed TOTP attempts, the entire session is destroyed (req.session.destroy()), requiring the user to re-authenticate with their primary credentials from scratch."

Q17 What is lazy card provisioning, and what architectural benefit does it provide?

"When a customer opens a bank account, an associated virtual debit card is not immediately written to the database. Instead, cardService.getOrCreate() queries for a card record; if none exists, it provisions a new card with a 4-year expiry and ₹25,000 daily limit on first access. This avoids unnecessary database writes and index overhead for customers who only use checking or savings accounts without debit cards."

Q18 How does your automated integration test suite work without colliding on database state?

"In server/tests/banking.test.js, integration tests run against the live Express app using Supertest. To ensure test isolation without database collisions, each test run generates a unique customer email salted with a high-resolution timestamp (testuser_${Date.now()}@bank.app). At the end of the test run, an afterAll hook executes await prisma.$disconnect() to cleanly drain the connection pool, preventing hung Jest processes."

Q19 Why do you separate server.js from app.js?

"Separation of concerns. app.js configures and exports the Express application (middlewares, security headers, routing, error handling) as a pure software component without binding physical network ports. server.js imports app.js and invokes app.listen(PORT). This separation allows Supertest in automated tests to import app directly into virtual memory and issue simulated HTTP requests without triggering port-in-use (EADDRINUSE) conflicts."

Q20 Explain how Helmet.js secures the Express application against common web vulnerabilities.

"Helmet injects 15+ HTTP response headers that protect against browser-based attacks: X-Frame-Options: DENY prevents clickjacking by forbidding embedding in iframes; X-Content-Type-Options: nosniff stops MIME-sniffing attacks; Strict-Transport-Security (HSTS) enforces HTTPS connections; and Referrer-Policy: no-referrer prevents leaking sensitive URLs in outgoing headers."

Q21 How do you enforce KYC age validation during user onboarding?

"In userService.js (registerUser), we compute the applicant's exact chronological age using their dateOfBirth against the current date: age = today.getFullYear() - birthDate.getFullYear(). If the applicant is under 18 years of age, the service immediately throws ApiException.badRequest('You must be at least 18 years old to open an account'), halting the transaction before any user or account record is committed."

Q22 What is the difference between optimistic and pessimistic UI updates in financial frontends?

"In social media apps (e.g. liking a tweet), optimistic updates mutate the UI immediately before the server responds. In financial applications, optimistic updates are dangerous: showing a deducted balance or completed transfer before backend validation can cause severe user panic if the server later returns Insufficient Funds or a network timeout. Swiss Bank uses strictly pessimistic UI updates: the UI only updates account balances and ledger entries after receiving HTTP 200/201 confirmation from the backend."

Q23 Why does PostgreSQL use BigInt for account numbers, and how do you serialize it in JavaScript?

"Bank account numbers are 10-digit integers (e.g. 1029384756) that exceed 32-bit integer limits (max 2,147,483,647). Therefore, PostgreSQL requires BigInt (64-bit signed integer). However, JavaScript's native JSON.stringify() throws a TypeError when encountering a BigInt: 'Do not know how to serialize a BigInt'. In Swiss Bank, we convert BigInt account numbers to standard JavaScript numbers (Number(accountNumber)) in our DTO transformation layer (toAccountResponse) before JSON serialization."

Q24 How does vercel.json handle client-side routing rewrites for Single Page Applications?

"In a React SPA with client-side routing (React Router), navigation between /dashboard and /login occurs without server round-trips. However, if a user refreshes /dashboard directly, the web server looks for a physical file /dashboard/index.html and returns a 404 error. The vercel.json configuration specifies a rewrite rule: { source: '/(.*)', destination: '/index.html' }, routing all incoming requests to the SPA root so React Router can render the correct view."

Q25 What is the purpose of BCrypt salt rounds, and why did you choose work factor 10?

"BCrypt incorporates an exponential cost factor (work factor). At work factor 10, the algorithm computes 2^10 = 1,024 hashing rounds. This introduces an intentional ~80-100ms computational delay per password check. This delay is negligible for legitimate users logging in once, but makes offline brute-force and dictionary attacks using GPU clusters computationally intractable."

Q26 How do you implement rate limiting and lockout on multi-factor authentication attempts?

"In authController.js, we track failed TOTP attempts on the user's session: req.session.mfaAttempts = (req.session.mfaAttempts || 0) + 1. If mfaAttempts reaches MAX_MFA_ATTEMPTS (5), the session is destroyed with req.session.destroy() and an HTTP 429 Too Many Requests response is returned, forcing the user to start over with their primary credentials."

Q27 What is Write-Ahead Logging (WAL) in PostgreSQL, and how does it guarantee durability?

"WAL is PostgreSQL's durability engine. Before any changes are written to physical table data files (heaps), a record describing the change is written to an append-only WAL log on disk and flushed with fsync. If the server loses power or crashes during a fund transfer, PostgreSQL reads the WAL upon reboot, replaying committed transactions (REDO) and rolling back uncommitted ones (UNDO), ensuring zero ledger corruption."

Q28 Which transaction isolation level does Swiss Bank use, and why?

"Swiss Bank runs on PostgreSQL's default Read Committed isolation level combined with explicit row-level write locks (SELECT ... FOR UPDATE). Explicit row locking provides the serialization safety required for fund transfers (preventing lost updates and race conditions) without the performance overhead and serialization failure retry loops of the Serializable isolation level."

Q29 How do foreign key cascade constraints protect data integrity when users or accounts are modified?

"In schema.prisma, relations define onDelete: Cascade. For example, if a user is purged for compliance or GDPR reasons, their associated accounts, ledger entries, debit cards, and tickets are automatically deleted in referential cascade, preventing dangling orphan records in child tables."

Q30 How does Swiss Bank implement the Controller-Service-Repository architectural pattern?

"Swiss Bank maintains strict separation of concerns across layers: (1) Routes define HTTP endpoints and attach security middlewares; (2) Controllers parse HTTP requests, extract parameters, and format HTTP responses; (3) Services encapsulate core business logic, validations, and transactional state mutations; (4) Prisma Client acts as the Repository/Data Access Layer, executing type-safe SQL queries against PostgreSQL."

Q31 How does your centralized error handler (errorHandler.js) protect against stack trace leakage?

"In errorHandler.js, all application errors are routed to a centralized Express error middleware. Custom domain errors extend ApiException with explicit HTTP status codes (e.g. 400 for validation, 404 for missing entities, 403 for IDOR violations).
